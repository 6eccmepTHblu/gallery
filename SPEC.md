# Gallery — спецификация v1

Быстрый просмотрщик-сортировщик изображений для Windows 11.

---

Этот файл — **единственный источник истины**. При расхождении между разделами
побеждает раздел [§4 «Карта клавиш»](#4-модель-взаимодействия) для поведения

## 1. Что мы строим

### 1.1 Юзкейс

Это **не** архивный менеджер фотографий. Это инструмент быстрого триажа: человек
листает папку изображений и одним хоткеем откладывает нужные в целевую папку.

Из этого выводится всё остальное:

1. **Переключение кадра должно быть мгновенным.** Это главная метрика продукта.
2. **Отклик хоткея — без задержки.** Не «быстро», а неотличимо от мгновенного.
3. **Ни одного модального диалога на горячем пути.** Ни подтверждений, ни выбора при
   конфликте имён, ни сообщений об ошибках. Диалог ломает ритм «клавиша — кадр — клавиша».
4. **Обратная связь не прерывает поток.** Человек нажмёт хоткей 200 раз за сессию —
   интерфейс, который на 200-м нажатии раздражает, спроектирован неверно.
5. **Отмена вместо подтверждения.** `Ctrl+Z` дешевле, чем «вы уверены?», и решает ту же
   задачу лучше (Nielsen: контроль и свобода пользователя).

### 1.2 Принцип проектирования

Минимализм. Не изобретать то, что уже есть в платформе. Не строить абстракций под
гипотетическое будущее. Самое короткое решение, которое работает.

Не экономить на: понимании задачи, обработке ошибок, доступности, производительности
горячего пути, целостности пользовательских данных.

### 1.3 Критерий успеха

Прогнать папку из 300 фотографий, разложив нужные по папкам, — и ни разу не задуматься
об интерфейсе.

## 2. Технологический стек

### 2.1 Решение

**WinUI 3 / Windows App SDK 2.4, C# на .NET 10, unpackaged self-contained.**

Решение принято судейством трёх независимых оценок (производительность, визуальное
качество, риск доведения до конца) над четырьмя проработанными вариантами. Разрыв
узкий: **7.9 / 7.5 / 7.4** из 10 у WinUI 3, Avalonia и WebView2 соответственно.
Узкий разрыв — причина, по которой §2.4 существует.

### 2.2 Почему

Единственный стек, чьи **дефолты совпадают с требованиями задачи**:

| Требование | Кто делает | Наш код |
|---|---|---|
| Все кодеки, установленные в системе, включая HEIC и RAW через Store-расширения | WIC | 0 |
| Зум с инерцией, панорамирование, rubber-band, pinch | `ScrollView` на InteractionTracker — **в потоке композитора, вне UI-потока** | ~6 строк XAML |
| Кастомный тайтлбар с корректными drag-регионами и Snap Layouts | `AppWindowTitleBar.ExtendsContentIntoTitleBar` | ~5 строк |
| Mica | `Window.SystemBackdrop = new MicaBackdrop()` | 1 строка |
| Тёмная/светлая/высококонтрастная тема, системный акцент | theme resources | 0 |
| UI Automation для скринридера, фокус-визуалы, Tab-навигация | XAML | 1 атрибут на элемент |
| Per-monitor DPI v2 | `app.manifest` | 3 строки |
| Один экземпляр приложения | `AppInstance.RedirectActivationToAsync` | ~10 строк |
| Текст — DirectWrite, Segoe UI Variable, субпиксельный ClearType | платформа | 0 |

Решающий аргумент — **доступ к WIC**. Каждый второй телефон снимает в HEIC, каждая
зеркалка — в RAW. Стек без WIC (Avalonia на Skia) на такой папке даёт не «медленно»,
а «не открывается вообще»; стек поверх браузерного движка (WebView2) вынужден строить
**второй** конвейер декодирования через WIC с дисковым кэшем прокси-JPEG — то есть
проходит горячий путь дважды и через диск.

Второй аргумент — зум и панорамирование. У Avalonia это ~60 самых баг-опасных строк
проекта (zoom-to-cursor, клампинг пана по границам, fit-on-load, сброс при смене кадра),
и инерции с rubber-band у ручной реализации не будет. Здесь это конфигурация.

### 2.3 Что мы за это платим — честно

| Цена | Величина | Смягчение |
|---|---|---|
| Размер дистрибутива | **213,2 МБ / 451 файл** или **227,3 МБ одним exe** (замерено, self-contained + R2R на компонентных пакетах). Без R2R — 169,6 МБ, но старт вдвое хуже (§2.4) | Это пол, ниже не опуститься. `PublishTrimmed` и NativeAOT для WinUI XAML не поддерживаются — **как и для WPF** (`NETSDK1168`), это паритет, а не проигрыш |

| Диагностика | XAML-компилятор врёт. **Замерено в этой сессии:** обычная ошибка C# (`CS0246`, забытый `using`) уронила его в `Xaml Internal Error WMC9999: Ссылка на объект не указывает на экземпляр объекта` | При непонятной ошибке XAML — сначала искать обычную ошибку C# |
| Помощь ИИ-ассистента | Материала по WinUI 3 на порядок меньше, чем по WPF; половина найденного относится к UWP/WinUI 2 и неприменима | Сверяться с `learn.microsoft.com`, не с памятью модели |
| Риск тупика | Баг XAML-слоя обойти нечем — исходников нет, фикс приезжает через 1–3 месяца | §2.4 |
| Nearest-neighbor при зуме | **Невозможен.** В WinUI 3 нет аналога `RenderOptions.BitmapScalingMode`, у `Image` и `CompositionSurfaceBrush` нет управления интерполяцией ([microsoft-ui-xaml#9380](https://github.com/microsoft/microsoft-ui-xaml/issues/9380)) | §6.6 — принято, билинейка на всех масштабах |
| Компонентные пакеты в lockstep | Версии расходятся (`WinUI 2.3.6`, `Foundation 2.3.9`, `InteractiveExperiences 2.1.6` внутри «2.4.0») и `Runtime` падает при несовпадении | Версии выуживаются из текста ошибки; ручная работа при каждом обновлении SDK |

**Ловушка размера:** meta-пакет `Microsoft.WindowsAppSDK` тянет `onnxruntime.dll`
(20,7 МБ) и `DirectML.dll` (17,8 МБ) даже без единой строки про ИИ. Ссылаться на
**компонентные** пакеты: 224,6 → 169,6 МБ.

### 2.4 Решение зафиксировано

WinUI 3 был оспорен отдельной проработкой WPF с собственными замерами (§2.6) —
**решение подтверждено владельцем проекта и пересмотру не подлежит.** Раздел существует,
чтобы к этому спору не возвращаться.

**Веха 0 пройдена — гейт не сработал, стек подтверждён замером.**

Замерено до первого **отрисованного кадра** (`CompositionTarget.Rendering`), а не до
создания HWND: HWND появляется раньше, чем XAML что-либо нарисовал, поэтому ходовая
цифра «старт WinUI 210 мс» измеряет не то.

| Сборка | Холодный | Тёплый (медиана 8) | Размер |
|---|---:|---:|---|
| **self-contained + R2R, папка** | **885 мс** | **178 мс** (173–195) | 213,2 МБ / 451 файл |
| self-contained + R2R, single-file | 1120 мс | 205 мс (195–208) | 227,3 МБ / **1 файл** |
| self-contained **без R2R** | **1683 мс** ❌ | 208 мс (201–215) | 169,6 МБ / 451 файл |

Working set на первом кадре — 93–99 МБ, private 74,6 МБ.

> **`PublishReadyToRun` обязателен, а не желателен.** Без него холодный старт 1683 мс —
> это **выше гейта в 1200 мс**, то есть сборка без R2R завалила бы выбор стека. R2R
> срезает холодный старт на 47% и стоит +43,6 МБ. Это не оптимизация «на потом»,
> это условие, при котором решение §2.1 остаётся в силе.

«Холодный» здесь — первый запуск после публикации при прогретом файловом кэше ОС.
Честный старт после перезагрузки не замерялся и будет выше; отдельного гейта на него
нет, но при первой же жалобе на медленный запуск мерить надо именно его.

### 2.5 Что принято вместе с этим решением

Два «бесплатных подарка» WinUI 3 частично исчезают на быстром пути декодирования, и это
надо знать сейчас, а не открыть на вехе 1.

`ExifOrientationMode.RespectExifOrientation` и `ColorManagementMode.ColorManageToSRgb`
живут на `GetSoftwareBitmapAsync` — **том самом API, который §6.3 признал самым медленным
из трёх**. Если веха 1 выберет быстрый путь, ориентация пишется руками (§8.4), а
управление цветом становится известным дефектом v1 (§8.5) — ровно как было бы в WPF.

Остаётся бесплатным и продолжает оправдывать выбор: зум и панорамирование **в потоке
композитора** (в WPF это ~62 строки плюс обязательная дисциплина «весь декод на
`Task.Run` + `Freeze()`», иначе пан дёргается при занятом UI-потоке), родной тайтлбар
со Snap Layouts, theme resources, UIA.

### 2.6 Отклонённые варианты

| Стек | Оценка | Почему нет |
|---|---|---|
| **Avalonia 12.1** | 7.5 | Skia даёт только PNG/JPEG/WebP/BMP/GIF. HEIC, AVIF, TIFF, RAW не открываются. Лечение — Magick.NET (+30 МБ, медленнее Skia) или WIC-интероп, то есть признание правоты WinUI. Плюс: нет display-aware color management (фото пересыщены на wide-gamut), нет субпиксельного ClearType, а Avalonia 12 (апрель 2026) переименовала оконный API, тогда как модели и StackOverflow помнят 11. **Единственное, в чём объективно лучше: декодер Skia быстрее WIC в 1,3–2,3× на каждом размере каждого реального файла** (замерено) |

| **Electron** | — | 80–150 МБ ради дублирования движка, который уже в системе |
| **WPF на .NET 10** | оспорил решение | Проработан отдельно, с собственным пробником. **Объективно лучше:** один exe 148,3 МБ вместо 169,6 МБ в 451 файле; 169 794 вопроса на Stack Overflow против 2 601 у обеих меток WinUI (**разрыв 65×**); API заморожен с 2006 года, поэтому ответы 2011 года компилируются сегодня; честная диагностика компилятора. **Цена:** старт 426 мс против ~210 мс (замерено, пол самого фреймворка 415 мс — Mica стоит 3 мс, Fluent-тема 11 мс, оптимизировать нечего); зум и пан на UI-потоке (~62 строки + дисциплина); EXIF-ориентация и ICC игнорируются (подтверждено замером: тег = 6, кадр отдаётся неповёрнутым); Fluent-тема помечена экспериментальной и требует `NoWarn WPF0001`; ClearType деградирует до серого сглаживания на Mica-окне; фреймворк в режиме сопровождения. **Попутно опровергнуто:** ходовая оценка «WPF даст 75–95 МБ» неверна — trimming и NativeAOT запрещены и в WPF тоже (`NETSDK1168`, проверено), реально 148 МБ. Решение владельца проекта — остаться на WinUI 3 |
| **Собственный D3D / SwapChainPanel** | — | Контент внутри swap chain для UIA не существует — полная потеря доступности. Плюс свои текстуры, DPI, hit-testing, математика зума |

### 2.7 Зависимости

**Один NuGet-пакет** — компонентные пакеты Windows App SDK. Всё остальное — BCL и WinRT.

Рассмотрено и отклонено: `CommunityToolkit.Mvvm` (одно окно, ~6 биндингов),
`WinUIEx` (`AppWindow.SetPresenter` — одна строка), `Microsoft.Graphics.Win2D`
(второй рендер-стек в приложении), `Magick.NET` / `SkiaSharp` / `ImageSharp`
(WIC уже даёт системные кодеки, которых у них нет), `Serilog` / `NLog`
(`File.AppendAllText` в crash.log), `SQLitePCLRaw` (системный thumbcache уже прогрет),
xunit (см. §9.5).

`Microsoft.Windows.CsWin32` — под вопросом: нужен, если §6.3 выберет прямой WIC.
Иначе 3 строки `LibraryImport` для `StrCmpLogicalW`.

## 3. Состав v1

### 3.1 Входит

1. Открытие: аргумент командной строки (файл или папка), drag&drop, `Ctrl+O` / `Ctrl+Shift+O`, «Открыть с помощью» (через argv, без записи в реестр).
2. Список кадров: папка ВМЕСТЕ С ПОДПАПКАМИ, натуральная сортировка сначала по папке, потом по имени — как в Проводнике.
3. Навигация: стрелки, `PgUp/PgDn`, `Home/End`, колесо, `F5`.
4. Зум и панорамирование: вписать / 1:1, зум к курсору, pinch, двойной клик, drag, `Esc`.
5. **Копирование в целевую папку**: `Space` в слот 1, цифры `1`…`9` в слоты 1–9, привязка папки первым нажатием, автоматическое разрешение конфликтов имён, отметка уже скопированных, `Ctrl+Z`.
6. Буфер обмена: `Ctrl+C` — файл.
7. Полноэкранный режим `F11`, автоскрытие хрома и курсора.
8. Панель настроек `Ctrl+,` (немодальная), `settings.json`.
9. Шпаргалка по клавишам `F1`.
10. Недавние папки `F7`: список папок с кадром, на котором каждую оставили.
11. Очистка от текста `F8`: поиск надписей, разметка букв, дорисовка под ними — по шагам, с кистью.
10. Тосты, карточки ошибок, доступность, упреждающая загрузка.
11. Отладочный оверлей `F12`, флаг `--bench`, флаг `--self-test`.
12. **Лента миниатюр** `T` / `F4`: текущий кадр в центре, переход кликом, настраиваемая непрозрачность (§4.8).

| Не делаем | Когда | Почему сейчас нет |

### 4.2 Почему `Space` — копирование, а не «следующий кадр»

Отступление от конвенции просмотрщиков ровно одно, и оно обосновано:

- Копирование — самое частое действие горячего пути; `Space` — самая крупная и быстрая
  клавиша (закон Фиттса применительно к клавиатуре).
- При `advanceAfterCopy = true` (по умолчанию) копирование **само переводит на следующий
  кадр** — то есть `Space` всё равно листает. Нарушение конвенции сглажено.
- Триаж сводится к двум клавишам одной руки: `Space` = «беру и дальше», `→` = «пропускаю».

Компенсация: строка в оверлее первого запуска и переключатель в настройках
«Пробел = следующий кадр» для мышечной памяти из других вьюеров.

### 4.3 Guard на автоповтор — предотвращение потери данных

> **Клавиши, изменяющие файлы (`Space`, `1`…`9`, `Ctrl+Z`), игнорируют автоповтор:**
> ```csharp
> if (e.KeyStatus.WasKeyDown) return;
> ```
> Навигационные клавиши автоповтор принимают.

Без этого придержанная на полсекунды `3` создаёт 15 копий. С `Shift+3` (перемещение,
v2) и `Del` (v2) то же самое разрушает исходную папку за долю секунды.

### 4.4 Фокус и акселераторы

Все команды — `KeyboardAccelerator` со `ScopeOwner = ImageCanvas`. Панель настроек
содержит текстовые поля путей; когда фокус внутри неё, акселераторы канваса не
срабатывают, и нажатие `3` в поле не копирует файл.

> **Ctrl+E доходит не всегда, и это не наша ошибка.** Измерено на машине
> разработки: при нажатии `Ctrl+E` окно получает код клавиши **67 (`C`) вместо
> 69 (`E`)**. Та же клавиша без `Ctrl` приходит как 69, `Ctrl+D` — как 68,
> `Ctrl+Shift+E` — как 69. Раскладка ни при чём: одинаково на русской и
> английской. То есть ровно одно сочетание переписывается в `Ctrl+C` где-то
> между клавиатурой и окном, и приложение видит уже подменённый код — отличить
> его от настоящего `Ctrl+C` невозможно.
>
> Путь к находке стоит записать, потому что три очевидных объяснения оказались
> ложными: разметка и сгенерированный код совпадали один в один; чистая
> пересборка без промежуточных файлов ничего не изменила; перенос акселератора
> в код и затем в `KeyDown` тоже. Диагноз дала только трассировка сырого кода
> клавиши в `KeyDown` — до неё все замеры читали `_lastCmd`, который обновляется
> не на каждой ветке, и показания отставали на одно нажатие.
>
> Исправить это изнутри приложения нельзя. Поэтому у действия появилось второе
> написание — `Ctrl+Shift+E`, оно проходит целым. `Ctrl+E` остался: на машине
> без перехвата он работает.

**Запятая в `Ctrl+,` распознаётся в двух написаниях.** На латинских раскладках это
`VK_OEM_COMMA`, на русской запятая набирается как `Shift` и клавиша `/?`
(`VK_OEM_2`) — измерено через `VkKeyScanEx`. Без второго написания подпись
`Ctrl+,` описывала бы клавишу, которой на русской клавиатуре нет: `VK_OEM_COMMA`
там печатает «б».

**Все `Ctrl`-сочетания разбираются в `KeyDown`, а не акселераторами.** Цифры,
`Space` и `Ctrl+Z` и так жили там ради `KeyStatus.WasKeyDown`, а держать одну
группу клавиш в двух механизмах — лишний повод для расхождений. Акселераторы
остались за одиночными клавишами, где они ведут себя безупречно.

### 4.5 Открытие контента

| Сценарий | Поведение |
|---|---|
| Без аргументов | Пустое состояние. Если в настройках есть `lastPath` — восстанавливаем папку **и позицию в ней** |
| `gallery.exe D:\foto\img_042.jpg` | Кадр показан **немедленно**; перечисление остальных файлов идёт в фоне, затем индекс корректируется. На папке в 10 000 файлов первый кадр не ждёт сканирования |
| `gallery.exe D:\foto\` | Первый файл по текущей сортировке |
| Drag&drop файла | Открывается его папка, позиция — на нём |
| Drag&drop папки | Открывается папка |
| Drop нескольких объектов | Берём первый, остальные игнорируем |
| Второй экземпляр | `AppInstance.FindOrRegisterForKey` + `RedirectActivationToAsync` — переиспользуем окно. 20 двойных кликов не должны дать 20 окон |

**Запуск без аргументов возвращает туда, где закончили — цепочкой, а не одной
проверкой.** «Последний файл» — самое хрупкое из того, что мы помним: его могли
переименовать, удалить или унести на диск, который сейчас не подключён. Порядок:
сам файл → его папка → последняя из запомненных папок, которая ещё существует.
Показать пустой холст, когда папка на месте, значит соврать, что открывать нечего.

### 4.6 Навигация

**Колесо — всегда навигация**, независимо от того, приближено изображение или нет:
контекстно-зависимое колесо ломает предсказуемость. Дельты тачпада накапливаются
до 120 единиц на шаг, иначе двухпальцевый скролл пролистывает пачку кадров.

**Границы папки — без цикла.** Конец папки — сигнал «сессия разбора закончена», цикл
его прячет и при зажатой `→` возвращает в уже обработанные кадры, провоцируя повторные
копии. На краю: упор + отскок 8 px (отключается при системном «уменьшить анимацию») +
тост `Последний файл · 1032`.

**Позиция помнится по папкам, а не одна на всё приложение.** Вернувшись во
вчерашнюю съёмку, человек должен попасть туда, где остановился *в ней*, а не туда,
где закрыл приложение сегодня. `Settings.FolderLast` — словарь «папка → путь кадра»,
ограниченный сотней записей; глобальный `LastPath` остался для запуска без аргументов.

**Позиция пишется НЕМЕДЛЕННО на оседании, без секунды покоя.** Общий дебаунс
настроек в секунду тут не экономил ничего: оседание индекса — само по себе
дебаунс, при автоповторе 30 Гц оно не наступает ни разу, а наступает ровно тогда,
когда человек остановился на кадре. Зато секунда ожидания теряла позицию, если
процесс снимали не штатно — диспетчером задач, выключением питания, падением.
Дебаунс остался для остальных настроек: там он защищает от ползунка
непрозрачности, который на перетаскивании шлёт события десятками в секунду.

> **Замерено.** Запись всего файла настроек: **0,96–1,3 мс** при двух запомненных
> папках (825 Б) и **1,2–1,7 мс** на предельной сотне (31,6 КБ). Серия из 40
> нажатий подряд с шагом 33 мс дала **одну** запись — оседание отработало как
> дебаунс. При 16 мс на кадр цена приемлема, и синхронная запись на UI-потоке
> не нуждается в выносе в фон: он стоил бы блокировки от гонки двух записей
> ради полутора миллисекунд.
>
> Проверено снятием процесса: пролистать девять кадров и убить приложение из
> диспетчера — позиция сохранена и в `LastPath`, и в `FolderLast`.

**Позиция пишется в двух местах, и оба обязательны.** На оседании индекса
(120 мс после шага) и на закрытии окна. Закрытие раньше писало только `LastPath`,
а `FolderLast` обновлялся лишь на оседании — и тот, кто закрывал приложение сразу
после шага, а так и закрывают, досмотрев кадр, оставлял в `FolderLast` предыдущий
кадр. Запуск без аргументов подхватывал верный `LastPath` и выглядел исправным,
но стоило открыть ту же папку явно, и человек попадал не туда, где кончил.
Теперь обе записи делает одна `SaveSession()`.

**Свежесть папок хранится отдельным списком `FolderOrder`, а не порядком словаря.**
Соблазн был очевидный: `Dictionary` в .NET перечисляет ключи в порядке вставки,
значит «поднять папку наверх» можно удалением и повторной вставкой. Не выходит —
`Remove` отдаёт слот в список свободных, и повторная вставка того же ключа
переиспользует его, возвращая ключ на прежнее место. Поймано самопроверкой, а не
глазами. От этого порядка зависят две вещи сразу: к какой папке вернуться при
запуске, если `LastPath` мёртв, и какую выбросить при переполнении сотни — без
явного списка часто открываемая папка вылетала бы первой, как самая давно
добавленная.

**Переход по номеру — клик по счётчику `N / M`.** Счётчик уже показывает позицию,
поэтому он же и есть точка входа: клик превращает его в поле ввода прямо в статус-баре.
Модальный диалог здесь был бы тяжелее задачи. Пока поле открыто, цифры принадлежат ему,
а не слотам копирования — иначе набор «12» скопировал бы кадр дважды.

**Сортировка** — натуральная по имени (`img_2` < `img_10`) через `StrCmpLogicalW` из
`shlwapi.dll`, а не своя реализация: порядок обязан совпадать с окном Проводника,
из которого пользователь пришёл. Порядок перечисления файловой системы не гарантирован —
сортируем всегда явно.

### 4.6.1 Подпапки

| Параметр | Решение |
|---|---|
| Обход | Рекурсивный, глубина до 8 уровней |
| Порядок | Сначала по папке, потом по имени внутри неё — обе натурально |
| Потолок | 20 000 кадров |
| Целевые папки копирования | Исключаются из обхода |
| Строка статуса | Папка ТЕКУЩЕГО кадра, а не корень обхода |

**Зачем.** Том комикса лежит главами: папка тома, внутри — `ch1`, `ch2`, `ch10`.
Бросить на окно папку тома и читать её подряд — ровно то, ради чего приложение
и писалось. Без рекурсии человеку пришлось бы открывать каждую главу руками и
терять место при переходе.

**Порядок — сначала папка, потом имя.** Корень идёт первым (его относительный
путь пуст), дальше главы в натуральном порядке, внутри главы — кадры. Сравнение
натуральное на обоих уровнях, иначе `ch10` встала бы перед `ch2`.

Ключи сортировки считаются ОДИН РАЗ, а не внутри компаратора: разбор пути на
двадцати тысячах кадров в n·log n сравнений заметен, в отличие от самого
сравнения.

**Целевые папки копирования исключены из обхода.** До рекурсии слот внутри
исходной папки был безобиден: перечисление его не видело. Теперь бы видело —
и каждая скопированная картинка появлялась бы в списке вторым экземпляром, а
после `F5` список рос бы сам собой. Стены сравниваются ПО ПРЕФИКСУ С
РАЗДЕЛИТЕЛЕМ: без него папка `out2` попала бы под стену `out`.

**Стена, накрывающая саму открытую папку или её предка, снимается.** Иначе
человек открывает целевую папку слота — и видит «в папке нет изображений» при
полной папке файлов, без единого намёка на причину. Стена нужна только для
ПОДпапок обхода.

**За открытой папкой идёт слежение.** Перечисление делается один раз, и без
слежения любая правка снаружи остаётся невидимой: положил файлы в пустую папку —
на экране по-прежнему «в папке нет изображений», и починка только через `F5`, о
котором надо ещё догадаться. События оседают 600 мс: копирование сотни файлов —
это сотня событий подряд, а перечитать надо один раз, когда всё улеглось.

Пока список НЕ пуст, вид не трогается: перечитываются список, лента и счётчик, а
кадр и его масштаб остаются как есть — иначе копия файла в соседнюю подпапку
сбрасывала бы увеличение под руками. Папка была пуста и наполнилась — карточка
уходит сама и показывается первый кадр. Исчез текущий кадр — показывается первый
из оставшихся. Тома, не поддерживающие слежение, пишут строку в журнал и живут
по-старому, через `F5`.

**Строка статуса показывает папку текущего кадра.** С подпапками корень обхода
и место картинки — разные вещи, а по кнопке человек ждёт вторую. Считается
строка только при СМЕНЕ папки: при автоповторе 30 Гц сокращать путь заново
было бы выброшенной работой на горячем пути (§6.6).

### 4.6.2 Недавние папки — F7

| Параметр | Решение |
|---|---|
| Что помнится | Кадр в КАЖДОЙ папке, а не только в последней |
| Открыть | Двойной щелчок или Enter на строке |
| Удалить строку | Кнопка в строке; на диске не трогается ничего |
| Исчезнувшие папки | Выбрасываются ПРИ ОТКРЫТИИ списка |

**Память по папкам была и раньше** — `FolderLast` хранит путь последнего кадра
для каждой папки, `FolderOrder` держит порядок обращения. Не было способа её
УВИДЕТЬ: чтобы вернуться во вчерашнюю папку, приходилось искать её в проводнике.
Список делает эту память видимой и адресуемой.

**Ключ — корень обхода, а не папка кадра.** С подпапками (§4.6.1) том с главами
это одна запись, а не двадцать: человек бросил на окно папку тома, ему и
возвращаться в том.

**Чистка — при открытии списка, а не в фоне по таймеру.** Внешний диск и сетевую
шару отключают и подключают обратно; вычищать их по расписанию значило бы терять
позиции у того, кто просто вынул флешку. А вот строка, по которой щёлкнули и
которая ведёт в никуда, — это тупик, поэтому проверка делается ровно тогда,
когда список показывают.

**Проверка существования передаётся снаружи** (`PruneMissing(Func<string,bool>)`).
Самопроверке ходить на диск нельзя, а без этого логику списка не проверить
числом: порядок, удаление строки, повторное удаление несуществующей.

**«Удалить» забывает И кадр, И место в порядке.** Убрать только `FolderLast`
недостаточно: папка осталась бы в `FolderOrder` и всплыла бы снова при
следующем обращении.

### 4.7 Зум и панорамирование

| Параметр | Решение |
|---|---|
| Шаг | Геометрический ×1.25 на щелчок колеса |
| Диапазон | от `min(вписать, 5%)` до 3200% |
| Якорь | **Зум к курсору**; при `+`/`-` — центр вьюпорта |
| Вписать (`F`) | По умолчанию для каждого нового кадра. **Не увеличивает** мелкие картинки выше 100% |
| 1:1 (`A`) | Пиксель в пиксель |
| Двойной клик | **Всегда «вписать»** — по той стороне, которая упирается первой. Переключатель «вписать ⇄ 100%» отвергнут: из глубокого зума выйти нечем, если второй клик уводит на 100% |
| Панорама | Drag ЛКМ (курсор `grab`/`grabbing`); `Ctrl+стрелки`, шаг 10% вьюпорта |
| Между кадрами | Зум сбрасывается в «вписать» — иначе при сортировке пользователь теряется |
| Прозрачность | `ponytail:` плоский `#2A2A2C` вместо шахматки. `ImageBrush` в WinUI 3 не тайлится, а генерировать шахматку под размер кадра — ~12 МБ на картинку ради косметики. Вернуться, если понадобится отличать прозрачное от серого |

**Реализация — `ScrollView` (WinUI 3), а не своя матрица.** Зум к курсору, инерция,
rubber-band и pinch идут на InteractionTracker в потоке композитора: пан не дёргается,
даже когда UI-поток занят декодом соседа. Своими руками это ~60 самых баг-опасных
строк проекта, и инерции у них всё равно не будет.

**Ключ к простоте: содержимое всегда имеет размер «вписать», поэтому `ZoomFactor == 1`
это ровно «вписать», а 1:1 — это `SrcW / fitW`.** Отдельного состояния режима не нужно:
режим выводится из одного числа, и процент считается той же формулой.

**Цена `ScrollView` оказалась выше объявленной — и обе статьи нашлись только
запуском, не чтением.**

1. **Колесо не перехватывается обработчиком.** `ScrollView` потребляет его на уровне
   `InteractionTracker`, *до* маршрутизации XAML, поэтому `AddHandler(...,
   handledEventsToo: true)` не получает событие вообще. Единственная рабочая ручка —
   `IgnoredInputKinds = ScrollingInputKinds.MouseWheel`. Плата: `Ctrl+колесо`
   перестаёт зумить само, и зум к курсору пишется руками — пять строк.
2. **`ExtentWidth`/`ExtentHeight` — размер содержимого ДО зума.** Прокручиваемая
   область равна экстенту, умноженному на `ZoomFactor`. Условие «панорамировать
   нечего», сравнивавшее голый экстент с вьюпортом, было истинно почти всегда, и
   перетаскивание не начиналось вовсе. Замер при ×3.81: экстент 401×602, вьюпорт
   1084×602 — без множителя прокрутка выходила нулевой, с множителем 444×1692.

Пан левой кнопкой (`ScrollView` его для мыши не делает) остался как был — десяток строк.

**Над лентой миниатюр колесо листает, а `Ctrl`+колесо не делает ничего.** Зумить
там нечего, а листать по `Ctrl`+колесу нельзя: один и тот же жест не должен означать
разное в соседних сантиметрах экрана.

**Путь к папке — под размером кадра, справа внизу, и он кликабелен.** Строка
отвечает на вопрос «откуда это показано», который иначе требует лезть в заголовок
или в `Ctrl+Shift+E`. Клик открывает папку в Проводнике — через текущий файл,
чтобы он там сразу подсветился. Длинный путь режется по СЕРЕДИНЕ и только по
разделителям (`D:\…\testdata\2026\сентябрь`): хвост — имя папки, ради которого
строка и нужна, а корень отвечает на «тот ли это диск»; обрезка по символам дала
бы бессмысленное `D:\…ects\Personal`. Считается на смене папки, а не в `Render()`:
тот зовётся до 30 раз в секунду, а папка за это время измениться не может.

**Индикатор зума — в статус-баре**, не отдельной пилюлей по центру: место уже есть,
элемент новый не нужен, при «вписать» и 100% индикатор скрыт как неинформативный.
Это закрывает развилку, помеченную критиком полноты.

Экстремальные пропорции (>8:1, панорама 20000×200): «вписать по обеим сторонам» даёт
полоску в 1 пиксель. В v1 — вписываем как есть и не изобретаем эвристику; `Fit Width` — v2.

### 4.8 Лента миниатюр

| Параметр | Решение |
|---|---|
| Положение | Накладка: снизу (по умолчанию) или справа — переключается в настройках |
| Центр | **Текущий кадр всегда в середине ряда** |
| Ячейка | 80×60, шаг 86, `Stretch=Uniform` — кадр вписан, не обрезан |
| Показ / скрытие | `T` и `F4`, состояние сохраняется |
| Непрозрачность | Ползунок 25…100 %, по умолчанию 90 %. В высокой контрастности принудительно 100 % |
| Переход | Клик по миниатюре (`PointerPressed`, не `Tapped`) |
| Колесо | Листание, как и везде (§4.6) |
| Движение | Сдвиг ряда 120 мс `easeOutQuint`, глушится при плотном потоке событий (§7.6) |
| Источник | Миниатюра оболочки, `ThumbnailMode.SingleItem`, 128 px |

**Снизу или справа.** Снизу по умолчанию: ось ленты совпадает с осью
«влево-вправо», которой человек листает, и так делают Lightroom, Bridge и Photos.
Справа выигрывает на широком экране с вертикальными кадрами — там дефицитна
высота, а её и ест нижняя лента. Обе стороны — один и тот же код: меняются
ориентация ряда, шаг (по ширине ячейки или по высоте) и ось сдвига. Отдельной
реализации не понадобилось.

**Текущий кадр всегда в центре — и отсюда следует вся простота.** У ленты нет
собственного состояния прокрутки: она чистая функция от `CurrentIndex`. Значит не
нужны ни `ScrollView`, ни `ItemsRepeater`, ни виртуализация — хватает ряда из 2K+1
ячеек, которым на каждом шаге переназначают `Source`. Ряд чуть шире окна, крайние
ячейки обрезаются его рамкой. За краем папки ячейка держит место, но пуста: иначе
ряд полз бы вбок на первых и последних кадрах, а центр обязан стоять.

Побочная выгода: `ScrollView` в этом проекте уже дважды обошёлся дорого (§4.7), и
лента с ним просто не встречается.

**Накладка, а не строка сетки.** Строка меняла бы высоту вьюпорта, а на ней держится
«вписать»: каждое нажатие `T` пересчитывало бы `LayoutFrame` и сбрасывало зум
пользователя. Накладка не вызывает переразметки вообще, и прозрачность у неё
осмысленна — кадр виден насквозь.

> **Цена решения, принимаемая вслух:** нижние ~78 px кадра закрыты и недоступны для
> панорамирования, пока лента показана. Это настоящая потеря, а не мелочь; выход —
> `T`. Альтернатива (строка сетки) стоила бы сброса зума на каждом переключении,
> что хуже.

**Миниатюры берёт оболочка, а не наш декодер.** `Decoder.ThumbnailAsync` читает
встроенную EXIF-миниатюру за 1–2 мс, и соблазн переиспользовать его велик — но он
**не применяет поворот**. На холсте это незаметно: заглушка живёт ~120 мс и сменяется
полным кадром. В ленте миниатюра постоянна, и каждый вертикальный кадр лежал бы
набок всё время работы — ровно та ошибка, которую §8.4 называет самой частой у
просмотрщиков. `StorageFile.GetThumbnailAsync` поворот применяет сам, умеет HEIC,
AVIF и RAW и держит собственный дисковый кэш: три задачи одним вызовом.

**`BitmapImage`, а не `SoftwareBitmapSource`.** Он не владеет чужим `SoftwareBitmap`
и не требует `Dispose`, поэтому вытеснение из кэша физически не может освободить
источник, который всё ещё висит в живой ячейке. Тот же класс ошибки уже стоил
проекту крэша `RO_E_CLOSED` (§6.4) — здесь он исключён по построению, а не
внимательностью.

**Две клавиши на одно действие.** `T` — потому что §4.1 зарезервировала её под ленту
ещё до того, как лента появилась. `F4` — потому что на русской раскладке клавиша `T`
подписана «е», и человек, читающий шпаргалку, её там не найдёт (§10.1). Одна клавиша
честна перед спецификацией, вторая — перед пользователем.

**Что НЕ делает лента.** Не заказывает миниатюры при автоповторе — только с осевшего
индекса, иначе очередь тонет в работе, которая устареет раньше, чем закончится. Не
переспрашивает файлы без миниатюры — их помнит отрицательный кэш. Не показывает
бейджи «уже скопировано»: счётчик и бейдж на холсте уже отвечают на этот вопрос, а
девять цветных точек на ячейке 80×60 превратили бы ленту в рябь. Не берёт
клавиатурный фокус: у каждого её действия есть клавиша, а два десятка безымянных
ячеек в дереве UIA — шум, поэтому весь блок помечен `AccessibilityView=Raw`.

**Замерено.** Лента стоит **+0,14 мс p50 и +2,3 мс p99** на смене кадра: 15
присваиваний `Image.Source` за шаг. Сравнение перед записью в `Opacity` и
`BorderBrush` сняло часть (p99 3,52 → 3,01 мс), остальное неустранимо. При 16 мс
на кадр это приемлемо, и цена платится только когда лента показана.

### 4.9 Распознавание текста на странице

| Параметр | Решение |
|---|---|
| Движок | **PP-OCRv5** на ONNX Runtime (RapidOcrNet, Apache-2.0), 13,7 МБ моделей |
| Запасной | `Windows.Media.Ocr` — если моделей рядом с бинарём не оказалось |
| Границы реплик | Детектор облаков RT-DETRv2 (`ogkalu/comic-text-and-bubble-detector`), 11 МБ |
| Цвет подложки | Медиана пикселей ВНУТРИ облака |
| Шаг строки | Высота реплики / число сшитых строк, нижняя середина по странице |
| Порядок чтения | XY-cut, задаётся один раз — от него зависит контекст переводчика |

**Почему не встроенный движок Windows.** Он обучен на документах и на комиксном
леттеринге разваливается: 28,8 % ошибок в знаках против 3,3 % у PP-OCRv5 на
одном и том же корпусе. Крутилок, которые бы это исправили, у него нет — наружу
он отдаёт только язык и картинку. Остаётся запасным: работает без единого файла
моделей, а значит страница прочитается всегда.

**Замерено, корпус 12 страниц / 96 реплик, 4 начертания.**

| Начертание | Windows OCR: точно / ошибок | PP-OCRv5: точно / ошибок |
|---|---|---|
| Bangers | 2 из 24 / 59,4 % | **12 из 24 / 5,7 %** |
| Ink Free | 0 из 24 / 50,2 % | **15 из 24 / 4,6 %** |
| Comic Neue BI | 15 из 24 / 3,6 % | 15 из 24 / 2,4 % |
| Comic Sans BI | 16 из 24 / 2,2 % | **21 из 24 / 0,6 %** |
| **ВСЕГО** | 33 из 96 / **28,8 %** | **63 из 96 / 3,3 %** |

Время при этом НЕ выросло: страница 1100x1500 — около 1,0 с у обоих.

**Зачем детектор облаков, если движок сменился.** Он решает две задачи, которые
распознаватель не решает в принципе.

1. **Границы реплик.** PP-OCRv5 отдаёт СТРОКИ. «WHY AM I ALWAYS» и «THE ONLY ONE
   ON TIME...» — одна фраза, и порознь они переводятся в два обрывка. Где
   кончается реплика, знает форма облака, а не распознаватель.
2. **Подписи без пузыря.** Надпись прямо по рисунку детектор находит плохо:
   на странице 2000x2000 с двумя такими подписями он нашёл только водяной знак.
   Поэтому строки, которым облака не нашлось, сшиваются ПО ГЕОМЕТРИИ: заметное
   перекрытие по горизонтали плюс отсутствие просвета по вертикали. Обе проверки
   обязательны — только по вертикали склеятся подписи в разных углах кадра,
   только по горизонтали — соседние реплики одной колонки. Где детектор сказал
   своё слово, геометрия не вмешивается.

   Без этого «Mind / helping / me out?» уходило в перевод тремя обрывками и
   возвращалось как «Осторожно», «помощь», «Меня вытащили?» — тремя плашками
   друг поверх друга. Стало: одна реплика, «Не поможешь мне?».

3. **Цвет подложки.** Рамка строки жмётся к глифам вплотную; кольцо вокруг неё
   попадает уже на рисунок — подложка выходила небесно-голубой в белом пузыре.
   Медиана ВНУТРИ облака даёт настоящий цвет: текст занимает меньшую часть
   площади и уходит в хвост.

Сам по себе детектор точность чтения не поднял: он находит **8 из 8 пузырей на
каждой странице корпуса**, а общая ошибка от этого сдвинулась на 1,9 пункта.
Это и было доказательством, что узкое место — чтение, а не поиск.

**Грабли, на которые уже наступили.**

- Сравнение «разница больше половины высоты» НЕТРАНЗИТИВНО: `List.Sort` на таком
  компараторе переставляет строки произвольно, и реплика склеивается задом
  наперёд. Порядок обязан быть полным — Y, при совпадении X.
- Признак «фон остался белым» не годится как «фон не подобрался»: честно белый
  пузырь от неподобранного так не отличить. Список бесхозных реплик ведётся явно.
- Высоту строки нельзя брать из рамки распознавателя: на одной странице Windows
  даёт 19 px там, где PP-OCRv5 даёт 33. Кегль перевода считается от шага строки
  в реплике.
- Наложения рамок убираются ОТДЕЛЬНЫМ проходом: слияние сопоставляет одной рамке
  ровно одну встречную, и вторая ложится поверх — два перевода друг на друге.

Ключ `--page страница.png --legacy` гоняет тот же тракт запасным движком: иначе
сравнивать движки было бы нечем.

### 4.10 Перевод страницы через API

| Параметр | Решение |
|---|---|
| Что отправляется | Реплики страницы ЦЕЛИКОМ, пронумерованные, в порядке чтения |
| Формат | chat completions, совместимый с OpenAI — не привязка к поставщику |
| Настройка | Адрес, модель, ключ; по умолчанию перевод локальный |
| Ключ | Отдельный файл, шифрование DPAPI на учётную запись Windows |
| Отказ | Молча откатываемся на локальную модель и говорим причину |

**Страница уходит одним запросом — ради этого всё и делалось.** Порепличный
перевод не может согласовать род, число и обращение «ты/вы»: данных для этого
в отдельной реплике просто нет. «Sorry I'm late» — это подбрасывание монетки
между «опоздал» и «опоздала», и никакая модель тут не поможет, потому что
английский оригинал пола не содержит. Когда модель видит весь диалог страницы
разом, согласование получается само собой.

**Порядок чтения обязателен, иначе контекст вреден.** Реплики упорядочиваются
рекурсивным XY-разрезом по рамкам самих пузырей — без выделения панелей:
межпанельные промежутки и так пусты, разрез находит их сам, а детектор панелей
был бы отдельной моделью с отдельными способами ошибаться. Ошибка порядка тихая
и дорогая: перевод остаётся связным на вид, но реплика достаётся другому
персонажу, и род согласуется не с тем.

**Подложки не налезают друг на друга.** Русский текст длиннее английского, и
место под него добирается ростом плашки. Расти вслепую нельзя: в колонке
реплик — а в комиксе они почти всегда колонкой — плашка наезжает на соседнюю, и
нечитаемы становятся обе. Поэтому рамки считаются в ДВА прохода: сначала все
исходные, потом рост, ограниченный полосой, свободной от соседей. Соседями
считаются только пересекающиеся ПО ГОРИЗОНТАЛИ — реплика в другой колонке
росту не мешает.

Запас по вертикали при этом почти нулевой — 1 % высоты против 6 % по
горизонтали: сверху и снизу почти всегда сосед, и лишние поля съедают именно
его место, а выносные элементы букв закрываются и малым отступом.

Воздух над и под текстом, который остаётся, — это НЕ отступ: плашка обязана
закрывать распознанную область целиком, и когда перевод короче оригинала,
разница видна как пустое поле. Уменьшать её дальше значит показывать исходный
текст из-под подложки.

Если полоса оказалась у́же самой рамки, плашка остаётся на месте и не
сдвигается: подложка обязана закрывать исходный текст, а сползшая вверх пустая
плашка хуже, чем задетый край соседа.

**Карточка персонажей живёт на папку.** Модель дописывает её сама и получает
обратно на следующей странице: кто какого рода, кто к кому на «ты». Том читают
подряд, и это знание обязано переживать смену страницы.

**Сопоставление строго по номерам, а не по порядку.** Модель может переставить
строки или потерять одну; принять её ответ позиционно значит сдвинуть перевод на
соседний пузырь — худшее, что здесь может случиться, потому что страница будет
выглядеть переведённой. Недостающие реплики добираются локальной моделью: смесь
лучше дыр.

**Текст страницы — данные, а не указания.** Он пришёл из чужого файла, и в нём
может быть написано что угодно, включая обращение к модели. В системном блоке
это заявлено прямо, а сам текст уходит полем JSON, а не склеенным в инструкцию.

> **Чего API не чинит.** Полноты. Звуки, вывески и текст по дуге не видит
> Windows OCR, а значит их не увидит и модель — ей отправляют то, что нашли.
> Это лечится только мультимодальным путём, где уходит сама картинка.

### 4.14 Очистка страницы от текста — F8

| Шаг | Чем | Что видно |
|---|---|---|
| 1. Найти текст | сегментатор по всей странице + рамки распознавания | рамки надписей контуром |
| 2. Разметить буквы | сегментатор по вырезке вокруг каждой надписи | полупрозрачная заливка по глифам |
| 3. Дорисовать | lama-manga | результат |

**Почему шаги разделены.** Стирание необратимо ПО СМЫСЛУ: пропущенную букву
видно только до дорисовки — после неё сравнивать уже не с чем, а «кажется,
что-то съелось» не проверить ничем. Поэтому человек сперва смотрит, что
нашлось, потом что размечено, и лишь затем разрешает стереть. Кнопка «Сделать
всё» — для случая, когда доверия уже хватает.

**Работа идёт и ПО БЛОКАМ, а не только по странице целиком.** На странице из
десяти надписей одна выходит плохо, и переделывать из-за неё всё — значит
терять девять удавшихся. Поэтому блок выбирается щелчком, размечается и
дорисовывается сам по себе, а неудачная попытка откатывается, не трогая
остальное.

| Инструмент «Рамка» | Что делает |
|---|---|
| Щелчок по рамке | выбрать блок; из вложенных — самый тесный |
| Перетаскивание по пустому месту | новая рамка там, где текст не нашли |

**Клавиатура повторяет порядок работы: сверху вниз и слева направо.** Ряд цифр
— вся страница, верхний ряд — инструмент, домашний ряд — действия над блоком.
Сперва берут инструмент, потом им работают — ряды идут в том же порядке:

| Клавиша | Что делает |
|---|---|
| **1** / **2** / **3** | найти текст / разметить буквы / дорисовать — вся страница |
| **4** | убрать ВСЕ рамки |
| **Q** / **W** / **E** | разметка: рамка / кисть / ластик |
| **Z** / **X** / **C** / **V** / **B** | рисование: пипетка / карандаш / линия / квадрат / круг |
| **A** | разметить блок |
| **S** | дорисовать — блок, а если блок не выбран, всё размеченное |
| **G** | залить размеченное градиентом (для гладкого фона) |
| **D** (или **Delete**) | убрать рамку |
| **F** | убрать разметку — в блоке или всю |
| **F1**, пока держите | исходник без единого элемента поверх |
| **Y** или **Ctrl+Z** | отменить |
| **Ctrl+Shift+Z** | вернуть отменённое |
| **Ctrl+S** | сохранить рядом, без вопросов и поверх прошлого сохранения |
| **Ctrl+Shift+S** | перезаписать ОРИГИНАЛ |

Исходник живёт на F1, а не на букве: буквенные ряды заняты работой, а эта
клавиша стоит особняком и нажимается не глядя. Пока панель открыта, F1
принадлежит ей, а не шпаргалке.

Клавиша спрашивает у СВОЕЙ кнопки, можно ли сейчас: занятость и «блок не
выбран» уже посчитаны там, второй копии этих условий нет. Автоповтор
игнорируется — удержание A это «задумался», а не «размечай пять раз подряд».
Подпись каждой кнопки несёт свою клавишу; у инструментов клавиша ушла в
заголовок раздела, потому что в трети колонки «Ластик (R)» обрезается.

**Перезапись оригинала НЕОБРАТИМА**, поэтому у неё отдельное сочетание, а не
«перезаписать, если файл уже есть». Пишется в формате самого файла: png-байты
в файле .jpg открылись бы не везде.

| Мышь | Что делает |
|---|---|
| Колесо | увеличение — точка под курсором остаётся под курсором |
| Ctrl+колесо | размер кисти, ластика или пера — того, что в руке |
| Левая кнопка, потянуть | двигать кадр |
| Двойной щелчок левой | вписать кадр |
| Правая кнопка | работает выбранным инструментом — и разметка, и рисование |
| Правая за край выбранной рамки | менять её размер |

Колесо без модификатора отдано увеличению, а не размеру кисти: по странице
ездят постоянно, а размер меняют изредка. Левая кнопка тянет кадр так же, как
в самом просмотрщике за панелью, — рука не переучивается.

Пока панель открыта, наружу не проходят ни T, ни F, ни F1: снаружи это лента,
вписывание и шпаргалка, и без этого F молча сбрасывала бы масштаб НЕВИДИМОГО
кадра за панелью заодно с уборкой разметки. «Вписать» в панели осталось
кнопкой: клавиша ушла под уборку разметки, а панель и так открывается
вписанной. Ctrl+Z снаружи отменяет файловые операции — при открытой панели он
туда уже не доходит. Цифры снаружи копируют кадр в слот — при открытой панели
тоже нет.

**Отмена с выбранным блоком откатывает ТОЛЬКО его.** Из трёх дорисованных
блоков два выходят хорошо, и терять их из-за третьего незачем: выбрал неудачный,
Ctrl+Z — вернулся он один, соседние остались чистыми. Запись при этом остаётся
в стеке, так что соседние блоки можно откатить по одному или все разом, сняв
выбор. Возврат (Ctrl+Shift+Z) работает той же операцией: применить запись и
положить обратную в соседний стек — разница только в том, откуда взяли и куда
положили. Любое новое действие обрывает ветку возврата.

**«Залить градиентом» — для гладкого фона, рядом с дорисовкой.** Сеть
восстанавливает ТЕКСТУРУ, и на текстуре она хороша. На гладком фоне — кожа,
небо, стена, любой плавный переход — текстуры нет, есть градиент, и сеть кладёт
туда ровный тон, усреднённый по округе. На глаз это «еле заметный шлейф» ровно
по форме бывших букв: тон сам по себе правдоподобный, но он не течёт вместе с
фоном.

Заливка решает уравнение Лапласа внутри разметки с краями из окружающих
пикселей. Гармоническая функция — самая гладкая поверхность, которая сходится к
заданным краям: слева край тянет свой цвет, справа свой, внутри они перетекают
друг в друга. Никакой модели для этого не нужно, считается за миллисекунды.

Решается пирамидой, а не в лоб: на дыре в пол-экрана простые проходы
протаскивают краевой цвет к середине по пикселю за проход, и их нужны тысячи. На
уменьшенной копии тот же путь — десяток пикселей, поэтому грубое решение
считается сразу, а точное только уточняет его. Проверка на самом себе: дыра
32x24 в линейном градиенте зарастает тем же градиентом с ошибкой меньше 1/255.

Замер на живой странице (розовый фон со шлейфом от стёртых букв, 965x827):
отклонение от гладкого фона в зоне шлейфа **1.18 → 0.17** при максимуме
**10.4 → 1.8** единиц яркости, 225 мс. Глазом шлейф исчезает полностью.

**Рисование по кадру: пипетка, карандаш, линия, квадрат, круг (Z X C V B).**
Отдельный раздел панели: разметка говорит «что стереть», а это правка самих
пикселей.

Почему вообще рука. Дорисовщик восстанавливает то, что СЛЕДУЕТ из окружения:
он видит по краям дыры плитку и заливает плиткой. Замер на живом кадре:
lama-manga (206 МБ), обычная LaMa (208 МБ), MI-GAN (28 МБ) и классика OpenCV —
все четыре одинаково НЕ провели оборванный шов, хотя на контрольной задаче, где
шов входит в дыру с двух сторон, все четверо восстанавливают его безупречно
(ошибка 2.8–7.1 из 255). Информации «линия идёт вот туда» в кадре нет — она
есть только у человека.

Две попытки обойтись без руки провалились и удалены. Полоса замеренного цвета
читается как наклейка: у настоящей линии есть размытие и неровность. Копия
живого куска линии вдоль направления тащит за собой и фон источника, и соседние
детали — на стыке швов в след попадает вторая линия.

Что делает ручную правку незаметной, и оба пункта обязательны: **цвет берётся
пипеткой ИЗ КАДРА** (подобранный на глаз всегда мимо: на сжатой картинке даже
ровная заливка гуляет на единицы) и **край мазка смягчён на полпикселя** (резкая
граница поверх сжатой картинки читается как наклейка). Пипетка берёт медиану
3x3, а не один пиксель: одиночный отсчёт может оказаться артефактом сжатия.

На ШТРИХОВОМ рисунке — рамка кадра, контур облачка, чёрная линия по белому —
рука побеждает вчистую: там нет ни зерна, ни градиента, которые надо
подделывать, есть ровный цвет и ровная толщина.

Карандаш копится в буфере и попадает в кадр ОДНОЙ записью отмены на штрих:
иначе каждый рывок мыши был бы своей записью и стек вымывался бы за один мазок.
Предпросмотр штриха идёт в слой разметки — перекладывать весь кадр на каждое
движение мыши слишком дорого. Слой при этом НЕ перерисовывается целиком, пока
ведут карандашом: перерисовка начинается с очистки слоя и стирала штрих в том
же обработчике, где он рисовался.

Предпросмотр линии, квадрата и круга идёт толщиной пера, а не в пиксель: иначе
при пере в 8 px человек выбирает место по волоску, а получает полосу. Круг под
курсором показывает след и у пера — с поправкой на то, что у кисти ползунок
задаёт радиус, а у пера толщину.

**Край выбранной рамки тянется, и это видно.** На выбранной рамке нарисованы
восемь ручек — четыре угла и середины сторон. Угол тянет две стороны сразу.
Сторона упирается в противоположную, а не проскакивает её: рамка, вывернутая
наизнанку, — не то, что человек имел в виду, потянув край. Размер в подписи
меняется на глазах, а в стек отмены ложится ОДНА запись на всю протяжку, а не
на каждое движение мыши.

Ручка рисуется контуром и НЕ ШИРЕ полосы захвата: сплошной квадрат закрывал бы
разметку под собой, а нарисованное шире хватаемого — ловушка, нажатие по краю
такой ручки рисовало бы новую рамку вместо правки старой. Полоса и ручка
считаются одной формулой (`Cleanup.Band`), на мелкой рамке обе ужимаются до
трети её размера — иначе рамка целиком стала бы «краем» и её нельзя было бы
выбрать щелчком.

Тянуть можно только ВЫБРАННУЮ рамку: они лежат внахлёст, и «та, что под
курсором» слишком часто оказывалась бы не той.

**Пока тянут мышью, клавиши молчат.** Они меняют тот самый список рамок и ту
самую разметку, которые держит протяжка: Delete посреди протяжки убирал рамку,
а протяжка дотягивала уже несуществующую — с падением по индексу. Протяжка к
тому же сверяется с рамкой, какой оставила её последним движением: список могли
подменить извне (шаг «найти текст», начатый ДО протяжки, доезжает и кладёт
новый) — тогда протяжка молча отпускает.

**«Убрать все рамки» — отдельной кнопкой в разделе всей страницы.** Поиск на
пёстрой странице находит десяток лишних рамок, и выбрасывать их по одной —
работа ради работы. Разметка при этом остаётся: рамки и разметка — разные вещи,
и человек мог уже поправить её кистью.

**Панель открывается ВПИСАННОЙ, всегда.** ZoomFit при показе панели делить не
на что — размеры прокрутки ещё нулевые, — поэтому страница открывалась в 1:1 и
первым делом её приходилось вписывать руками. Теперь вписывание ждёт первой
раскладки.

**Размеры кисти и ластика помнятся между запусками и ПОРОЗНЬ.** Инструменты
делают разное: кистью дорисовывают пропущенный хвост буквы, ластиком сметают
лишнее пятно — удобные размеры у них разные, и один общий ползунок заставлял бы
перекручивать его на каждое переключение. Ползунок принадлежит тому, что сейчас
в руке, и подпись под ним говорит, чей это размер. «Рамка» не рисует, при ней
ползунок показывает кисть: следующий мазок будет ею. Пишется с дебаунсом:
Ctrl+колесо шлёт события пачкой.

**Пока идёт работа, сверху слева крутится кружок.** Дорисовка занимает от
десятых долей секунды до нескольких секунд, и без него непонятно, думает она
или уже всё.

**Панель идёт за кадром.** Стрелки листают папку и при открытой панели: сохранил
страницу, нажал вправо — панель уже на следующей. Перезагрузка висит на том же
«оседании», что и запись позиции (120 мс после последнего шага), а не на самом
шаге: при автоповторе кадр меняется 30 раз в секунду, и декодировать страницу
на каждый незачем. Несохранённые правки при переходе теряются — о них
предупреждает всплывающая строка, а исходник на диске цел в любом случае.

**Сохранение перечитывает папку.** Поверх оригинала легли другие пиксели, а
рядом мог появиться новый файл — и то и другое приложение обязано показывать, а
не держать прежнее в кэше кадров и миниатюр. Тот же путь, что у F5, поэтому
сброс миниатюр достался и F5: раньше он обновлял список, а ряд внизу оставался
со старыми картинками.

**Под курсором кисти виден круг её размера.** Радиус задан в пикселях КАДРА, а
на экране зависит от увеличения — без круга размер мазка приходится угадывать и
проверять на самой странице. Круг живёт НАД прокруткой, в экранных координатах:
внутри неё обводка тянулась бы вместе с кадром и на 12x стала бы полосой.

**Кисть работает и до первой разметки.** Пустая разметка заводится первым же
мазком: «обвёл сам и стёр» — законный путь, а не ошибка. Раньше кисть до
разметки молча отказывала, и путь упирался в тупик.

**Дорисовка держится на РАЗМЕТКЕ, а не на выбранном блоке.** Блок выбран —
стирается только он; блок не выбран — всё размеченное, и кнопка так и
называется. Иначе обведённое кистью без рамки было нечем стереть: кнопка стояла
выключенной, а человек уже всё показал.

Рамка блока рисуется зелёной и втрое толще прочих: выбранный блок обязан
отличаться от остальных с одного взгляда, а не по подписи сбоку.

**Разметка блока ЗАМЕНЯЕТ прежнюю внутри своей рамки**, а снаружи не трогает —
иначе повторный проход по блоку накапливал бы мусор от прошлых попыток.

**Разметка не выходит за рамку.** Поля вокруг рамки идут в МОДЕЛЬ (выносные
элементы и хвосты букв нужны ей как опора), но не в разметку: рамку человек
провёл сам, и краска за её краем читается как промах — обвёл одну надпись,
разметилась она и кусок соседней. Рамки распознавания за это поле и
расширяются: они обтягивают строку вплотную, и без запаса обрезка съедала бы
хвосты. Что обведено, то и красится.

**После удачной дорисовки разметка гасится.** Краска поверх уже чистого места
читается как «текст остался», а повторная дорисовка прошлась бы по нему заново.

**Показ исходника по Q — держать, а не переключать.** Сравнение «до и после»
делается взглядом туда-обратно, и лишнее нажатие на возврат его сбивает. Пока
клавиша нажата, скрывается и разметка, и рамки: сравнивать надо кадр с кадром.
Масштаб и положение прокрутки при этом не трогаются вовсе — меняется только
содержимое слоёв, поэтому взгляд остаётся на том же месте страницы.

**Увеличение.** Кадр лежит в прокручиваемой области с масштабированием:
Ctrl+колесо приближает, кнопки «Вписать» и «1:1» дают опору. Координаты
указателя внутри остаются в пикселях КАДРА при любом масштабе — поэтому кисть
от увеличения не зависит вовсе, и радиус задаётся тоже в пикселях кадра.

**Разметка показана полупрозрачной, а не сплошной.** Сквозь неё должен читаться
сам текст: иначе непонятно, накрыта буква целиком или наполовину.

**Кисть правит РАЗМЕТКУ, а не кадр.** Правится решение «это буква», а не
пиксели страницы — поэтому мазок отменяется, а дорисовку можно повторить с
исправленной разметкой.

**Отмена одна на всё.** И мазок кистью, и правка рамок, и дорисовка блока ложатся
в ОДИН стек: два стека («отменить мазок» и «отменить блок») человеку пришлось бы
держать в голове, а порядок собственных действий он помнит и так. На кнопке
написано, что именно откатится. Откат дорисовки возвращает И пиксели, И разметку
под ними — иначе текст вернулся бы, а размечать его пришлось бы заново.

Снимок под откат берётся только с ОБЛАСТИ дорисовки, а не с кадра целиком:
двенадцать снимков страницы 2000x2000 — это под двести мегабайт впустую.

**Рамки рисуются ПОСЛЕ каждой правки слоя, а не один раз.** Мазок перекрашивает
свою полосу целиком по маске — и стирал зелёную линию под собой: со стороны
выглядело так, будто ластик убирает границу блока. Рисуется только периметр,
так что звать это на каждый мазок не жалко.

**Грабли панели.**

- Признак занятости — ПОЛЕ, а не состояние кнопок. `UpdateBlockInfo` зовётся из
  `Push`, то есть из каждого мазка кистью, и заново включал кнопки прямо посреди
  счёта: два прохода по одному кадру заканчивались тем, что первый освобождал
  битмап под вторым.
- Кадр НЕ освобождается, пока его читает фоновый шаг. И заливка, и дорисовка
  зовут `Copy()` уже после счёта, а листание стрелкой перезагружает панель —
  `Dispose` в этот момент означает обращение к мёртвому объекту из чужого
  потока, то есть падение, которое нечем поймать. Пока идёт счёт, ссылка просто
  отпускается.
- Разметка уходит в фоновый поток КОПИЕЙ. Иначе мазки, нарисованные пока идёт
  счёт, стирались бы по его итогам, ничего под ними не залив.
- Заливка отказывается работать, если в разметке нет ни одного известного
  пикселя по краям: тянуть градиент неоткуда, а молча залить чёрным — худший из
  возможных ответов.
- Окно двойного щелчка берётся у системы (`GetDoubleClickTime`), якорь
  сбрасывается, как только кадр поехал, и левая кнопка не вмешивается, пока
  правой тянут рамку или ведут мазок.

- Клавиши ловятся на КОРНЕ окна, а не на самой панели: при щелчке по кадру
  фокус остаётся на холсте ЗА ней, и до панели событие не доходит вовсе.
  Поймано тем, что Delete не срабатывал ни разу.
- Состояние кнопок пересчитывается ПОСЛЕ присвоения разметки, а не до: запись
  в стек отмены делается раньше и тянула за собой устаревший пересчёт — кнопка
  «Убрать разметку» оставалась выключенной при готовой разметке.
- Пока панель открыта, цифры и пробел НЕ копируют кадр в слот. Иначе правка
  разметки оборачивалась бы файлами в целевой папке.
- Рамка прижимается к кадру СРАЗУ при рождении (`Cleanup.Clamp`). Тянут её с
  захватом указателя, и он свободно уходит за край кадра, а дальше рамка
  адресует маску страницы напрямую, по индексу на пиксель. Рамка снаружи =
  выход за массив: «Разметить блок», «Дорисовать блок» и «Убрать разметку»
  падали, причём последняя роняла приложение целиком (журнал за 18.09).

Мазок кладётся ОТРЕЗКОМ, а не точкой: указатель приходит рывками, и по точкам
быстрый мах оставлял бы пунктир. Перерисовывается только задетая полоса — полный
слой на кадре 2000x2000 это 16 МБ за движение, и рука начинает чувствовать
задержку.

**Модели.**

| | Размер | Лицензия |
|---|---|---|
| `TareHimself/comic-text-mask` — разметка букв | 57 МБ | MIT |
| `ogkalu/lama-manga-onnx-dynamic` — дорисовка | 206 МБ | MIT/Apache в карточках |

**Почему разметка — обученная модель, а не порог.** Порогом не выходит, и это
проверено тремя способами: по кайме рамки, морфологией по тонким штрихам и по
господствующему цвету надписи. Каждый валится на тексте поверх пёстрого рисунка,
и валится по-своему — то съедает лист растения и абажур, то оставляет буквы на
листве. Локально штрих буквы и край листа неотличимы; различить их можно, только
ЗНАЯ, как выглядят буквы.

**Замерено на восьми кадрах** (локальный SSD, 12 потоков):

| | |
|---|---|
| Поиск надписей | 70–450 мс |
| Разметка букв | 60–360 мс |
| Дорисовка | 180–1050 мс |
| Построение сессий | около 6 с, ОДИН раз |

Сессии строятся заранее и в фоне при открытии панели: платить шесть секунд
ожиданием ПОСЛЕ нажатия «Дорисовать» значит выдавать загрузку за работу.

**Грабли.**

- Стороны вырезки под дорисовку обязаны быть КРАТНЫ 8, иначе модель падает
  в `Mul` с несовпадением осей. Проверяется числом.
- Модель дорисовки склеивает результат с исходником САМА — вне маски отличие
  ровно ноль, смешивать вручную не надо и вредно.
- Источников рамок два, и они дополняют друг друга: на восьми пробных кадрах
  распознавание молчало на трёх, а сегментатор находил там текст сам. Рамки
  внахлёст складываются, иначе одна надпись считалась бы дважды.
- Исходный файл НЕ трогается никогда. «Сохранить рядом» кладёт копию с
  припиской `-clean`.

Ключ `gallery.exe --clean страница.png` (или папка) гоняет тот же тракт без окна
и кладёт рядом `-mask` и `-clean` — иначе проверять качество пришлось бы
скриншотами.

## 5. Копирование в целевую папку — ядро

### 5.1 Слоты

Модель данных — **массив из 9 слотов** (`string?[9]`). Это буквально массив вместо
скаляра; цена восьми дополнительных слотов ≈ 0, а цена неверно выбранной единственной
папки — второй проход по всей папке.

Пользователь, которому нужна одна папка, нажимает только `Space` и никогда не узнает,
что слоты есть. **Слот 1 — это и есть «место сохранения» из постановки задачи**, он
показан в статус-баре как чип с именем папки; слоты 2–9 — маленькие бейджи рядом.

**Привязка первым нажатием.** Нажали `3`, слот пуст → открывается системный пикер папки,
папка запоминается, **и файл сразу копируется**. Никакого «сначала зайдите в настройки».
Модальный диалог допустим только здесь — это холодный путь, один раз за слот.

Бейдж слота **всегда содержит цифру**, а не только цвет — иначе он не читается при
дальтонизме. Девять цветов — §7.4.

**Мышиный путь.** Бейджи слотов в статус-баре кликабельны: клик = копировать,
ПКМ = перепривязать. Зона нажатия ≥32×32, тултип содержит хоткей. Без этого у
пользователя с мышью нет способа сохранить файл вообще.

### 5.2 Конфликт имён — без единого вопроса

```
цель\имя.ext не существует        → копируем
существует, размер совпадает      → NO-OP, бейдж «уже там», в стек undo не кладём
существует, размер отличается     → имя (2).ext   (конвенция Проводника)
```

Диалог на горячем пути недопустим: в пакете из 300 файлов он превращается в 300 модальных
окон. Перезапись отвергнута — это тихая потеря данных без отмены. Проверка «имя + размер»
ловит главный случай (повторный прогон по той же папке) и не даёт расплодиться
`(2)`, `(3)`, `(4)`.

> `ponytail:` сравнение по имени+размеру, а не по хэшу. Апгрейд до SHA-256 — при первом
> ложном срабатывании на файлах одинакового размера.

### 5.3 Атомарность

Копируем во **временное имя в целевой папке**, затем `File.Move` (переименование внутри
тома — атомарно). В целевой папке никогда не появляется полуфайл, который другой процесс
может прочитать недописанным.

**Копия обязана быть байт-идентична оригиналу.** Никакого пересохранения повёрнутого
битмапа — это уничтожит EXIF, ICC, GPS и gain map. Проверяется хешем (§9.6).

### 5.4 Оптимистичный UI и очередь

Копия уходит в фоновую последовательную очередь (`Channel` + один потребитель). Бейдж и
переход к следующему кадру происходят **немедленно**, не дожидаясь диска. На локальном
SSD разницы нет; на сетевой шаре это разница между 0 мс и 150 мс на каждом кадре.

При провале бейдж краснеет, тост держится 6 с с настоящей причиной. Повтор = повторное
нажатие той же клавиши. При очереди >20 задач — счётчик в статус-баре, ввод не блокируется
никогда.

### 5.5 Закрытие при непустой очереди — предотвращение потери данных

> Оптимистичный UI сказал «сохранено», очередь фоновая, пользователь закрыл окно →
> копий нет, а бейджи их обещали.

`AppWindow.Closing`: если очередь непуста — отменить закрытие, показать
«Завершаю N операций…», дождаться с таймаутом 5 с, закрыться. При таймауте —
**единственный разрешённый в приложении модальный вопрос**: «N операций не завершены.
Закрыть?»

### 5.6 Отмена

`Ctrl+Z`, стек на 50 операций, в пределах сессии.

- Отмена копии → удаляем созданный файл **в Корзину**, а не `File.Delete`, и **только
  если он совпадает с тем, что мы записали** (размер + время записи). Не совпал →
  тост «Файл в «Печать» изменён — не трогаю» + кнопка «Открыть папку». Данные
  пользователя не теряются никогда.
- NO-OP-дубликаты в стек не попадают, чтобы `Ctrl+Z` не «пустовал».
- Отмена всегда возвращает вид на тот кадр, к которому относилась операция.

### 5.7 Отметка уже скопированных

При привязке слота и при `F5` имена файлов целевой папки складываются в `HashSet`
**в фоне, с отменой**. Файл, чьё имя есть в наборе, показывается с приглушённым бейджем.
Это даёт сохранение отметок между запусками бесплатно — без sidecar-файлов, без базы.

Ложное срабатывание при совпадении имён из разных папок допустимо: цена ошибки —
лишняя подсказка, не потеря данных.

**Кап 50 000 имён на слот.** Слот может указывать на архив с 200 000 файлов на NAS —
это минуты. При превышении отметки для слота отключаются, в тултипе одна строка об этом.

### 5.8 Целевая папка недоступна

Никаких проверок «до». Пробуем операцию, ловим исключение, показываем причину:

| Ситуация | Реакция |
|---|---|
| Папка исчезла (отключён диск, сеть) | Тост `Слот 2 недоступен · Ctrl+Shift+2 — выбрать заново`, бейдж красный, **привязка не стирается** |
| Нет прав | Тост с текстом ошибки, повтор = нажать клавишу снова |
| Диск заполнен | Тост `Недостаточно места`, временный файл удаляется |
| Медленная сеть | Ничего: очередь фоновая, растёт счётчик |
| Слишком длинный путь назначения | Тост, не модалка. Имя исходника + целевая папка легко переваливают 260 |
| Целевая папка == исходной | Обнаружить при привязке и не дать выбрать (сравнение нормализованных путей) |

### 5.9 Сверка с уже сохранённым

| Параметр | Решение |
|---|---|
| Что сверяется | Содержимое ПОБАЙТОВО, а не имя |
| Где | Целевая папка слота И ВСЕ ЕЁ ПОДПАПКИ |
| Индекс | Размер → пути; строится при привязке слота и по `F5` |
| Порог проб | 20 кандидатов одного размера |
| Итог | Копия не создаётся, показывается уведомление с путём |

**Почему индекс по размеру, а не по хешу.** Размер уже лежит в записи каталога:
обход дерева его отдаёт, не открывая ни одного файла. Замерено на локальном SSD
с прогретым кэшем каталога: **11 000 файлов/с**, то есть дерево в 10 000 кадров
индексируется за **0,9 с**. Ответ «такого нет» даётся вообще без чтения диска —
а это подавляющее большинство ответов.

Содержимое читается только при СОВПАДЕНИИ размера, и это редкость. Побайтовое
сравнение потоком идёт со скоростью диска: SHA-256 на той же машине даёт
**1 100 МБ/с**, то есть около **3 мс** на трёхмегабайтный файл.

**Чего эта сверка НЕ ловит: пересжатую или уменьшенную копию.** Для неё нужен
перцептивный хеш, а он требует распаковки каждого файла: замерено **3,7 мс на
страницу 2000x2000** при распаковке JPEG в 1/8 размера — около **37 с на 10 000
страниц**, разово и с кэшем. Это другой порядок цены, поэтому вынесено за рамки:
человек, пересматривающий свои же файлы, встречает именно побайтовые копии.

**Потолок проб.** Файлов одного размера может оказаться тысяча — например,
однотипные иконки. Читать их все на нажатии клавиши нельзя, поэтому сравнений
не больше двадцати: лучше не заметить дубликат, чем подвесить нажатие.

**Источник не может найти сам себя.** Слот вполне может смотреть на ту же папку,
из которой идёт просмотр; путь, равный исходному, из кандидатов исключается.

**Уведомление не гаснет само и не затирается.** «Уже есть» отвечает на вопрос
«почему не скопировалось», и пропустить его нельзя — поэтому у тоста жёлтая
рамка, кнопка закрытия и никакого таймера. Отдельно пришлось запретить фоновым
сообщениям его затирать: упор в конец папки показывал «Последний файл» поверх
предупреждения, и на последнем кадре главы ответ пропадал.

### 5.10 Рецепты для v2

Оба — по одной строке, поэтому и отложены без сожаления:

- **Перемещение**: копия во временное имя → `File.Move` → удаление исходника. Между
  томами `File.Move` = копирование + удаление, не атомарно; провал на середине →
  временный файл удаляется, элемент возвращается в список.
- **Корзина**: `Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile(path, UIOption.OnlyErrorDialogs, RecycleOption.SendToRecycleBin)`.
  Одна строка, в составе .NET, без `SHFileOperation` P/Invoke.

## 6. Архитектура и горячий путь

### 6.1 Единственный источник истины

> **`currentPath` — источник истины. Индекс производен от него, не наоборот.**

После любой мутации списка (файл удалён снаружи, перемещён, папка пересканирована)
позиция восстанавливается по пути; если путь исчез — берётся элемент с тем же индексом
с клампом по границам. **Кадр перерисовывается до того, как принимается следующая
клавиша**: ввод отбрасывается, пока показанный кадр ≠ текущему пути.

Без этого правила после выреза элемента индекс указывает на *следующий* файл, а
пользователь видит предыдущий кадр и жмёт `2` — скопируется не то, что на экране.

### 6.2 UI-поток

**Ноль исключений:** UI-поток только присваивает готовый битмап и анимирует.
Ни декода, ни IO, ни перечисления, ни хеширования.

### 6.3 Конвейер декодирования — открытая развилка, закрывается на вехе 1

Здесь находится самая дорогая ошибка проекта, и она уже найдена — до написания кода.

**Замерено на трёх реальных фото** (best-of-5, файл целиком в памяти, декод в BGRA8,
материализация пикселей форсирована):

| Файл | Путь | native | 1/2 | 1/4 | 1/8 |
|---|---|---:|---:|---:|---:|
| 3312×5888, 19,5 МП, baseline | `BitmapDecoder` + `BitmapTransform` | 119 | 117 | 102 | **99** |
| | `BitmapImage.DecodePixelWidth` (WIC) | 255 | 116 | 77 | **60** |
| | Skia `SKCodec` | 142 | 92 | 68 | **52** |
| 5824×3264, 19,0 МП, baseline | `BitmapDecoder` + `BitmapTransform` | 192 | 184 | 154 | **158** |
| | `BitmapImage.DecodePixelWidth` | 298 | 164 | 120 | **96** |
| 3840×2160, 8,3 МП, **progressive** | `BitmapDecoder` + `BitmapTransform` | 231 | 216 | 210 | **206** |
| | `BitmapImage.DecodePixelWidth` | 238 | 169 | 149 | **147** |
| | Skia `SKCodec` | 120 | 94 | 77 | **68** |

**Вывод 1.** `Windows.Graphics.Imaging.BitmapDecoder` + `BitmapTransform`
**не делает scaled decode в DCT-домене**. Он декодирует полный кадр и потом масштабирует:
выигрыш 1,12–1,22× при уменьшении в **восемь раз** — это подпись «полный декод + скейлер».
Настоящий scaled decode (через `IWICBitmapSourceTransform`, куда ходит `DecodePixelWidth`)
даёт 4,25× на том же файле. **Самый очевидный API оказался самым медленным путём.**

**Вывод 2.** Прогрессивный JPEG — скрытая мина. Файл на 8,3 МП (в 2,3 раза меньше
остальных) стоил WIC 231 мс, дороже 19-мегапиксельных, и остался 206 мс даже при 1/8:
прогрессивный поток требует многопроходного энтропийного декода всего кадра, и
`IWICBitmapSourceTransform` на нём бесполезен. Картинки, скачанные из веба, часто
прогрессивные.

**Вывод 3.** 19 МП JPEG на этом CPU не опустить ниже ~90 мс никакими трюками.
Причина техническая: WIC умеет пропустить обратное ДКП и сборку полноразмерного буфера,
но **энтропийное декодирование Хаффмана пропустить нельзя** — его надо прогнать по всему
файлу целиком. Значит **префетч — не оптимизация, а единственный механизм мгновенности.**

**Вывод 4 — правило степени двойки верно, но применять его нельзя.**
Замерено на 24 МП: `DecodePixelWidth=2560` медленнее, чем `=3000` — 124 против 118 мс,
потому что 6000→3000 это точный ДКП-масштаб 1/2, а 2560 — 1/2 плюс лишний ресэмплинг.

**Но на вехе 3 это правило пришлось отменить.** Оно ломается на границе тира: исходник
4000 px при цели 2048 даёт 1/2 = 2000, что ниже цели, поэтому деление не применяется
вообще и кадр декодируется в нативном разрешении. Замерено: **91 МБ на кадр вместо 24**,
кэш 640 МБ на семи кадрах, RSS 771 МБ.

> **Действующее правило: декодировать ровно в целевой размер, никогда не увеличивая.**
> Вчетверо памяти ради 5% времени — плохой размен, тем более что время всё равно
> скрыто префетчем. После смены: кадр 24 МБ, кэш ровно в бюджете 384 МБ, RSS 571 МБ.

### 6.3.1 Развилка закрыта на вехе 1 — путь A

**Замерено на корпусе §10.2, цель 2560 px, лучшее из 5 прогонов, мс:**

| Файл | МП | **A:** `GetSoftwareBitmapAsync`<br>+EXIF +ICC | A2: то же<br>без ICC | **B:** `BitmapImage`<br>`DecodePixelWidth` |
|---|---:|---:|---:|---:|
| 24 МП JPEG, шумный (13,9 МБ) | 24,0 | **149,2** | 148,1 | 157,0 |
| 24 МП JPEG, гладкий (3,3 МБ) | 24,0 | **78,7** | 77,4 | 84,4 |
| 8,3 МП JPEG, **прогрессивный** | 8,3 | 169,4 | 167,7 | 170,7 |
| 24 МП PNG | 24,0 | 140,6 | 140,6 | **131,0** |
| Обрезанный на 60% | 24,0 | 66,8 | 67,4 | 69,9 |

> **Решение: путь A.** На рабочей точке он не медленнее B, а на JPEG даже быстрее — и
> отдаёт EXIF-ориентацию и управление цветом бесплатно, одним вызовом.

**Почему это противоречит §6.3 и почему противоречие мнимое.** Замер судьи показывал,
что `BitmapDecoder + BitmapTransform` не масштабируется: 119→99 мс при делении на 8,
тогда как `DecodePixelWidth` давал 255→60. Оба замера верны. Дело в рабочей точке:

- у A низкие фиксированные расходы и **плохое** масштабирование;
- у B высокие фиксированные расходы и **хорошее** масштабирование;
- на 1/1 выигрывает A (119 против 255), на 1/8 — B (99 против 60), а **на 1/2 ничья**
  (117 против 116 у судьи, 149 против 157 у нас).

Приложение живёт на 1/2: 6000 px при цели 2560 даёт деление на 2. Вывод «A — самый
медленный путь» верен для масштаба, в котором мы не работаем.

> **Граница, о которой надо помнить.** Прогноз был: придёт лента миниатюр с целью
> ~256 px = 1/8, и на ней станет выгоден путь B. Лента пришла (§4.8), а развилка не
> открылась — миниатюры делает оболочка, наш декодер к ним вообще не причастен.
> Развилка остаётся живой для сетки (v2), если её миниатюры придётся рисовать самим.

**Следствие 1: управление цветом входит в v1.** ICC-конвертация стоит **1,1 мс**
(разница A и A2 в пределах шума). Записанный в §8.5 «известный дефект» отменяется:
`ColorManagementMode.ColorManageToSRgb` включён всегда, Adobe RGB не поедет в
пересыщенные.

**Следствие 2: EXIF-ориентация пишется не руками.**
`ExifOrientationMode.RespectExifOrientation` закрывает все восемь значений и
двойной поворот HEIC (§8.4) одним параметром.

**Следствие 3: прогрессивный JPEG подтверждён как мина.** 8,3 МП прогрессивного стоят
169 мс — дороже, чем 24 МП baseline (149 мс). Втрое дороже на пиксель, и ни один путь
это не лечит.

**Обязательно независимо от выбора:** файл читается **целиком в буфер** и декодируется
из памяти. Декодер, читающий файл мелкими порциями, на SMB-шаре даёт 400 мс вместо 40.

### 6.4 Тиры и память

Из файла порождаем **два** продукта, а не четыре — тир `preview` выкинут вместе с лентой
миниатюр (§3.2):

| Продукт | Размер | Потребитель | RAM |
|---|---|---|---|
| `frame` | вьюпорт × DPI, квантованный | главный холст | **17,5 МБ** на 2560×1707 BGRA |
| `full` | нативный | зум глубже `frame` | 96 МБ на 24 МП |

`full` создаётся только по запросу зума, живёт в единственном экземпляре и умирает при
смене кадра.

**Мгновенный плейсхолдер — встроенная EXIF-миниатюра, а не системная.**

**Замерено на вехе 1: `BitmapDecoder.GetThumbnailAsync()` отдаёт встроенную миниатюру
за 1,1–2,4 мс** — в 60 раз быстрее полного декода. Не нужен COM-интероп и нет
зависимости от того, заходил ли пользователь в эту папку Проводником.

**Но она есть не у всех файлов.** В том же замере миниатюра нашлась у baseline-JPEG и
не нашлась у прогрессивного JPEG и у PNG; `GetPreviewAsync()` не вернул ничего ни разу.
Значит это оптимистичный путь, а не основной — фолбэк обязателен.

Это и есть «мгновенный отклик»: миниатюра за 0,5 мс → полный кадр подменяет её через
~120 мс. Пользователь никогда не видит пустоту.

**Фолбэк** — системная миниатюра
`GetThumbnailAsync(ThumbnailMode.SingleItem, 256, ThumbnailOptions.ReturnOnlyIfCached)`
для форматов без встроенного превью (PNG, часть WebP). Флаг «только из кэша» обязателен:
без него вызов уходит в генерацию и блокирует поток на сотни мс. Побочная выгода — шелл
отдаёт превью HEIC, AVIF и RAW даже там, где наш декодер спотыкается.

Осторожно: **EXIF-миниатюра имеет собственную ориентацию.** Не применять к ней тег
основного изображения.

**Квантование тира — иначе кэш умирает при любом ресайзе.** Ключ кэша включает тир,
тир квантован по ступеням `1024 / 1600 / 2048 / 2560 / 3200 / 4096`. При ресайзе окна,
максимизации, `F11` или переезде на монитор с другим DPI: показываем текущий битмап
растянутым, дебаунс 250 мс, затем перезапрос текущего кадра в новом тире. Кэш соседей
не инвалидируется — пересоберётся естественно.

### 6.5 Кэш и префетч

**Кэш кадров: 384 МБ константой.** Вытеснение — **по расстоянию от текущего индекса**,
не по LRU. При линейном листании они совпадают, но при развороте направления LRU
выбрасывает ровно те кадры, к которым пользователь сейчас пойдёт назад. Реализация:
при вставке вытесняем запись с максимальным `|index − current|`. Окно ±3 закреплено
и не вытесняется никогда.

Арифметика: 6 соседей × 17,5 МБ = 105 МБ. Бюджета хватает с запасом на историю.

> `ponytail:` 384 МБ константой, не `min(512 МБ, 20% RAM)`. Адаптивность — если кто-то
> запустит на машине с 4 ГБ и пожалуется.

**Префетч: +3 вперёд / −2 назад**, окно зеркалится при развороте направления в течение
одного кадра.

**Кэшируется `SoftwareBitmapSource`, а не `SoftwareBitmap`.** `SetBitmapAsync`
копирует кадр в композиционную поверхность; если платить эту цену на каждом
переключении, попадание в кэш стоит 15–30 мс вместо нуля. С кэшем источников
попадание — это присваивание `Img.Source`, замерено **p50 0,10 мс / p99 0,18 мс**.

> **`SetBitmapAsync` забирает владение `SoftwareBitmap`.** Явный `Dispose` битмапа
> после него — двойное освобождение, и XAML позже падает с `RO_E_CLOSED`
> (крэш `0xC000027B` в `Microsoft.UI.Xaml.dll`, поймано на вехе 3 через журнал событий:
> managed-обработчики stowed exception не ловят). Освобождать нужно только источник.

**Кадр стоит вдвое больше декодированных байт** — сам битмап во владении источника
плюс композиционная поверхность. Учитывать в бюджете надо именно удвоенный размер,
иначе промах по памяти ровно вдвое.

**Предохранитель на закреплённое окно.** Если кадры оказались крупнее ожидаемого и
±3 в сумме дают больше двух бюджетов, закрепление ужимается до ±1 — иначе память
уезжает за потолок, а закрепление формально соблюдено.

`SoftwareBitmap` держит буфер в **нативной** памяти — ловушка Large Object Heap
и фризов от gen2-сборок исчезает сама.

### 6.6 Отмена при быстром листании

Автоповтор клавиши в Windows — **~30 Гц** после задержки 250–500 мс. Декодировать
33 мс/кадр невозможно ни при каком конвейере. Наивная реализация в этот момент забивает
очередь на сотни элементов и вешает UI на секунды после отпускания клавиши.

**Механизм — три сущности, не пять:**

```
одна SemaphoreSlim(4)
один CancellationTokenSource на текущую навигацию
таймер-дебаунс 120 мс
```

Смена индекса: `Cancel()` → пересоздать CTS → перерисовать из кэша или шелл-миниатюры →
взвести таймер. Декод стартует только для «осевшего» индекса.

**Skim-режим получается сам собой**: при 30 Гц таймер не срабатывает ни разу.
Отдельной сущности для него не нужно.

Счётчик поколений (epoch), резервация слота под P0 и четырёхуровневый приоритетный
канал — **выкинуты**: первый дублирует токен, второй не нужен (слоты свободны после
отмены), третий не нужен (после удаления ленты приоритетов два).

**Дедупликация:** ключ `(path, mtime, tier)` → задача in-flight; второй запрос
подписывается на результат, а не запускает второй декод.

### 6.7 Зум: фильтрация

`Image` в WinUI 3 при апскейле использует билинейную фильтрацию композитора, и
управления интерполяцией **нет** ([microsoft-ui-xaml#9380](https://github.com/microsoft/microsoft-ui-xaml/issues/9380)).
Nearest-neighbor достижим только через Win2D — это новая зависимость и другой класс
архитектуры рендера.

> `ponytail:` билинейка на всех масштабах, интерполяция при апскейле выше 100% будет
> мылить. Переезд на Win2D — когда кто-то реально пожалуется.

**Но до 100% картинка честная.** Кадр в кэше декодирован под тир; когда зум уходит
глубже его пикселей, показывать было бы нечего кроме растянутого тира. Поэтому по
достижении порога запрашивается полноразмерный декод — разово, с задержкой 150 мс
после остановки жеста, в единственном экземпляре, умирает при смене кадра.
Проверено на вехе 2: на 24 МП кадре при 117% источник переключается на `full`.

**Минификации сильнее 2× не допускаем:** `frame` декодируется под текущий вьюпорт,
поэтому отображаемый масштаб всегда в `[0.5, 1.0]`. Это заменяет и mipmap, и тайлы.

**Лимит текстуры D3D — 16384 px.** Отображаемый битмап всегда ≤8192 по каждой стороне,
иначе панорама 20000 px не загрузится и покажет пусто. Тайловый ре-декод — v2.

### 6.8 Целевые числа

Горячий путь — нарушение равно провалу продукта:

| Метрика | p50 | p99 | Статус |
|---|---|---|---|
| **Смена кадра, сосед в кэше** | ≤ 30 мс | ≤ 50 мс | цель |
| Смена кадра, промах: до какого-либо изображения | ≤ 40 мс | ≤ 80 мс | цель |
| Смена кадра, промах: до резкого кадра | ≤ 160 мс | ≤ 300 мс | цель |
| **Хоткей копирования → визуальное подтверждение** | ≤ 50 мс | ≤ 80 мс | цель |
| Попадание в префетч при dwell > 400 мс | ≥ 95% | — | цель |
| FPS при зажатой стрелке | 60 | без просадок ниже 50 | цель |

> «0 мс на переключение кадра» — фикция. `SoftwareBitmapSource.SetBitmapAsync` копирует
> 17–20 МБ в композиционную поверхность, плюс кадр композитора. Реально **15–30 мс**.
> Бюджеты выше это учитывают.

Старт и открытие:

| Сценарий | Цель | Статус |
|---|---|---|
| Холодный старт → первый кадр (пустое окно) | **885 мс** | **замерено, веха 0** |
| Тёплый старт → первый кадр (пустое окно) | **178 мс** | **замерено, веха 0** |
| Холодный старт → первый кадр **изображения** | ≤ 1100 мс | цель (885 + декод) |
| Открытие папки 1 000 файлов: годна к работе | ≤ 300 мс | цель |
| Первый кадр **не блокируется** перечислением | обязательно | правило |

Ресурсы:

| Метрика | Цель | Потолок |
|---|---|---|
| RSS: одно изображение, простой | ≤ 200 МБ | 300 МБ |
| RSS: листание папки 10k | ≤ 700 МБ | **1 ГБ жёстко** |
| **CPU в простое** | **0%** | — |

Нулевой CPU в простое — не косметика: приложение держат открытым часами. Никаких
таймеров опроса, никакого render-loop, никаких «дышащих» плейсхолдеров после загрузки.

### 6.9 Отладочный оверлей `F12`

Пять счётчиков, не двадцать:

1. Латентность последней смены кадра, **раздельно для попаданий и промахов** (смешанная метрика бесполезна).
2. Источник последнего кадра: `cache` / `shell-thumb` / `fresh-decode`.
3. Декодов запущено / отменено. **Сигнал здоровья — не «доля отменённых высокая», а
   «декодов почти не запускалось»:** замерено на вехе 3, 200 шагов с интервалом 33 мс
   дали **7 запущенных декодов и 0 отменённых**. Дебаунс не даёт декоду стартовать
   вовсе, и это строго лучше, чем стартовать и отменять.
4. МБ в кэше кадров / бюджет.
5. RSS.

### 6.10 Бенч без UI-автоматизации

Флаг `--bench <N>`: приложение само гоняет навигацию **через ту же команду, что и
клавиша**, пишет CSV в `%LocalAppData%\Gallery\bench.csv` и выходит. Никакого `SendInput`,
никакой UI-автоматизации WinUI 3.

## 7. UI/UX

### 7.1 Принцип

**Изображение — единственный постоянный объект на экране. Всё остальное появляется по
запросу и исчезает.** Интерфейс оценивается одной метрикой: сколько миллисекунд и
движений между «увидел кадр» и «отложил кадр».

### 7.2 Раскладка

```
┌───────────────────────────────────────────────────────────────┐
│ ▓ зона наведения «верх», 56px ─────────────── [– □ ×] системные│
│   ┌──────────────────────────────────────────────┐            │
│   │ 128/940 · DSC_0491.jpg              ⚙        │ 40px, pill │
│   └──────────────────────────────────────────────┘            │
│                                                                │
│ ▓│                                                   ✓ 20px │▓ │
│ ▓│                   И З О Б Р А Ж Е Н И Е              │▓ │
│ ◀│                (вписать, нейтральный фон)            │▶ │
│ ▓│  зоны 15% ширины                                      │▓ │
│                                                                │
│              ┌────────────────────────────────┐   137%        │
│              │ Скопировано в Печать · Ctrl+Z  │  ← тост-слот  │
│              └────────────────────────────────┘   (1 шт.)     │
│  ┌──────────────────────────────────────────────────────────┐ │
│  │ → Печать 47   ② ③ ④           2560×1707 · 4,2 МБ · 137% │ │  статус-бар
│  └──────────────────────────────────────────────────────────┘ │
├───────────────────────────────────────────────────────────────┤
│ ▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬───────────────  хайрлайн позиции, 2px    │
└───────────────────────────────────────────────────────────────┘
```

**Постоянно на экране** — только хайрлайн позиции: полоса 2 px по нижней кромке,
заполнена на `index/count`, акцентный цвет при `opacity 0.5`. Стоит ноль внимания,
отвечает на «где я в папке».

**Поведение хрома.** Верхняя капсула и статус-бар появляются при входе курсора в свою
зону (задержка 0 мс) и скрываются через 2400 мс без движения мыши. Не скрываются, пока
курсор над ними, открыт флайаут или фокус клавиатуры внутри. Движение внутри изображения
без входа в зоны хром не возвращает — иначе панель мигает при панорамировании.
Курсор прячется через 2000 мс покоя. `Tab` вызывает хром и ставит фокус.

**Минимальный размер окна: 640×400.** Ниже статус-бар с девятью бейджами не помещается —
схлопывается до чипа слота 1 и счётчика.

### 7.3 Эвристики Нильсена — конкретно

| Эвристика | Решение в этом интерфейсе |
|---|---|
| **Видимость состояния** | Хайрлайн позиции всегда; счётчик `128 / 940` табличными цифрами; чип слота 1 с именем папки; бейдж-галочка на кадре = «файл уже в целевой папке» — это **состояние**, а не событие, оно остаётся при возврате к кадру |
| **Язык системы** | «Скопировано в «Печать»», «Отменить», «Открыть папку». Никаких «экспорт», «синхронизация», «коллекция». Порядок кадров = порядок Проводника. Зум в процентах, а не «уровнях» |
| **Контроль и свобода** | `Ctrl+Z` вместо диалога подтверждения. `Esc` — один слоистый «шаг назад». Ни одного модального окна на горячем пути; пикер папки — единственный системный диалог |
| **Единообразие** | Все клавиатурные конвенции Windows соблюдены. Отступление одно — `Space`, обосновано в §4.2 |
| **Предотвращение ошибок** | Целевая папка проверяется в момент выбора, а не при первом копировании — ошибка всплывает, когда пользователь спокоен. Повторное сохранение идемпотентно. Конфликт имён → автопереименование, никогда перезапись. Целевая ≠ исходной. Guard на автоповтор (§4.3) |
| **Узнавание вместо припоминания** | Имя целевой папки написано на чипе всегда, не спрятано в настройках. Хоткей напечатан на самой кнопке и в тосте. Тултипы с хоткеем, задержка 600 мс. `F1` — шпаргалка |
| **Гибкость** | Всё делается с клавиатуры без единого клика. Всё сохраняющее — доступно и мышью (§5.1). `advanceAfterCopy` превращает триаж в одну клавишу |
| **Эстетика и минимализм** | Ноль хрома в покое. Пять элементов в раскрытой капсуле. Ни рамок, ни градиентов, ни виньеток вокруг фотографии — только хайрлайн `#FFFFFF @ 6%`, чтобы тёмное фото не слилось с фоном. Один акцент + один зелёный + один красный |
| **Работа с ошибками** | Формула: **что случилось → почему → одна кнопка действия**. Код ошибки — в тултипе «Подробнее», не в тексте. Ошибочный тост красный, **не исчезает сам**. Чип слота одновременно краснеет — причина видна и после закрытия тоста |
| **Справка** | Первый запуск: три строки поверх пустого состояния, не мастер и не тур. `F1` — шпаргалка. Больше документации в интерфейсе нет |

### 7.4 Законы

**Фиттса.** Цель — либо нулевая дистанция, либо бесконечная ширина. Хоткеи дают D→0 для
100% действий — это главное применение закона здесь. Шевроны прижаты к краям окна на всю
высоту. Зоны наведения 56 / 120 px вместо кнопок 24 px. Минимальная зона нажатия
32×32 при иконке 16.

**Хика.** Верхняя капсула — ровно 5 элементов, шестое не добавляется никогда.
Настройки — на одном экране без вкладок. На горячем пути выбор бинарный.

**Доэрти (<400 мс).** Всё медленнее 400 мс обязано иметь индикатор; всё быстрее 100 мс
обязано не иметь его вовсе — мигание индикатора хуже ожидания. Бюджеты — §6.8.

**Миллера.** Одновременно на экране максимум 5 элементов хрома. Счётчик `128 / 940`,
а не словами. Шпаргалка — 4 группы по ≤6 строк (с появлением слотов карта клавиш
переросла три группы, и это учтено).

### 7.5 Визуальный язык

**Материалы.** Фон канваса — **плоский непрозрачный нейтраль, без Mica**. Mica подмешивает
цвет обоев и даёт паразитный оттенок вокруг фотографии — недопустимо для просмотра
изображений, плюс это лишний слой прозрачности в композиции на каждом кадре. Mica живёт
только на полосе заголовка при пустом состоянии.

In-app акрил (размывает саму фотографию под собой) — на капсуле, статус-баре, тосте,
флайауте настроек, шпаргалке. При системном «уменьшить прозрачность» → сплошная заливка.

> **Инвариант: текст никогда не лежит на голом изображении.** Любая подпись имеет под
> собой акрил или скрим ≥60%. Это то, что гарантирует контраст поверх произвольного фото.

**Палитра — тёмная тема (по умолчанию).** Тема по умолчанию тёмная, не «системная»:
просмотр изображений — тот случай, где отклонение оправдано. Переключатель
«Система / Тёмная / Светлая» в настройках.

| Токен | HEX | Применение |
|---|---|---|
| `canvas` | `#141414` | Фон под изображением, строго нейтральный (R=G=B) |

**Палитра — светлая тема:** `canvas #ECECEC` (не белый: белый фон завышает воспринимаемую

`text-primary #1A1A1C`, `text-secondary #5B5B60`, `accent` = `SystemAccentColorDark1`,

получает тень `0 2px 12px rgba(0,0,0,0.10)`, контурный хайрлайн выключается; в тёмной —
наоборот.

**Девять цветов слотов** — фиксированы по индексу, не настраиваются, все проверены на
≥3:1 к `surface`:

| `#4CC2FF` | `#3DDC97` | `#FFC53D` | `#FF8A65` | `#B98EFF` | `#4DD0E1` | `#F06292` | `#AED581` | `#A1887F` |

Цвет — **вторичный** признак. Первичный — цифра на бейдже (§5.1).

**Скругления:** кнопки, поля, чипы — 4 px (`ControlCornerRadius`); панели, тост,

индикатор зума, счётчик — pill; бейдж «сохранено» — круг.

**Тени:** флайауты `0 8px 24px rgba(0,0,0,0.45)` в тёмной, `0.12` в светлой + внутренний
верхний хайрлайн `inset 0 1px 0 rgba(255,255,255,0.08)` — то, что делает акрил
«стеклянным», а не «мутным». Изображение теней не имеет (кроме светлой темы).

**Типографика** — Segoe UI Variable, fallback Segoe UI:

| Body | 14 / 20 | 400 | Тост, ошибки, настройки |

**Сетка отступов** — база 4 px, шкала `4 · 8 · 12 · 16 · 24 · 32 · 48`, ничего вне шкалы.

Иконки — Segoe Fluent Icons, 16 px в хроме, 20 в карточках, 48 в пустых состояниях.

### 7.6 Движение

Кривые Fluent: `decelerate` `cubic-bezier(0.1,0.9,0.2,1)` — появление;
`accelerate` `cubic-bezier(0.7,0,1,0.5)` — исчезновение;
`standard` `cubic-bezier(0.8,0,0.2,1)` — перемещение;
`easeOutQuint` `cubic-bezier(0.22,1,0.36,1)` — шаг зума.

| Переход | Длительность | Кривая |
|---|---|---|
| **Смена кадра** | **0 мс** | — |
| Из blur-плейсхолдера в резкий кадр | 60 мс opacity | decelerate |
| Появление хрома | 120 мс opacity + translateY 4 px | decelerate |
| Скрытие хрома | 180 мс opacity, задержка 2400 мс | accelerate |
| Тост появление / исчезновение | 160 / 120 мс | decelerate / accelerate |
| Вспышка «сохранено» по кромке | 90 in / 60 hold / 220 out | decelerate → accelerate |
| Появление бейджа-галочки | 180 мс scale 0.8→1.06→1.0 | decelerate |
| Шаг зума (`+`, `−`, двойной клик) | 120 мс | easeOutQuint |
| Плавный зум (колесо/трекпад) | **0 мс** | — |
| Флайаут настроек / шпаргалка | 150 мс opacity + 8 px | decelerate |

**Что не анимируем принципиально:**

1. **Смену кадра.** Кроссфейд между фото — это +80…150 мс к воспринимаемой задержке,
   гостинг двух картинок и полная каша при удержании стрелки. Прямая подмена.
2. **Всё при автоповторе клавиши**: при интервале между событиями <180 мс глушим анимации
   хрома, бейджей, отскока — только блит.
3. Панорамирование и жестовый зум (любая интерполяция = лаг).
4. Параллакс, пружины, «дыхание» кнопок, анимированные заставки.

**Уменьшенная анимация** — `UISettings.AnimationsEnabled`, подписка на изменение в
рантайме. При выключенных: все `translate` и `scale` → 0 мс; opacity ограничивается
80 мс (полностью убирать нельзя — смена состояния станет незаметной); вспышка кромки →
статичная обводка 2 px на 400 мс; бейдж появляется мгновенно; отскок на границе отключается.

### 7.7 Обратная связь при копировании — расчёт на 200 нажатий

Три канала, разнесённые по стоимости внимания.

**Канал 1 — периферийный, каждое нажатие, ~0 внимания.** Вспышка по кромке окна:
инсет-обводка 2 px цветом слота, 90/60/220 мс. Ловится боковым зрением, не заставляет
переводить взгляд с фотографии.

**Канал 2 — стойкое состояние, читается взглядом.** Бейдж 20 px в правом верхнем углу
кадра: круг цвета слота с **цифрой**. Это не уведомление, это факт — он отвечает на
«а этот я уже отложил?» при возврате назад.

**Канал 3 — тост, один слот, который переиспользуется.** Ключевое правило: **тост не
стекается.**

- Копирование №1: тост въезжает, `Скопировано в Печать · Отменить Ctrl+Z`, автозакрытие 4 с.
- Копирования №2…N, пока тост жив: **текст меняется на месте** (`Скопировано: 12 файлов · Отменить последнее Ctrl+Z`),
  анимации входа нет, таймер сбрасывается. Ни одного лишнего движения на экране.
- **Тихий режим:** после 25 успешных копирований или после первого фактического
  использования `Ctrl+Z` тост переходит в короткий вид — 1200 мс, opacity 0.7, только
  счётчик. Счётчик хранится в настройках, сбрасывается при смене целевой папки.
- Ошибки из тихого режима исключены: ошибочный тост всегда полный, красный,
  не самозакрывается.

Итог на 200 нажатиях: 200 периферийных вспышек, 200 стойких бейджей, **1–3 тоста**
вместо 200.

Отвергнуто: звук (в тишине бесит, в наушниках перекрывает), центральный оверлей-галочка
(перекрывает фото — то, ради чего человек здесь), стек тостов (за 10 секунд закрывает
экран), диалог подтверждения (убивает горячий путь, undo решает ту же задачу лучше).

### 7.8 Состояния

**Первый запуск / нет папки.** Mica-фон (единственное место, где он уместен), по центру
колонка, gap 16: иконка 48 px `text-tertiary` → Title 28/36 «Откройте папку с
изображениями» → Body `text-secondary` «Перетащите папку сюда или нажмите `Ctrl+O`» →
primary-кнопка 32 px «Выбрать папку» + текстовая «Горячие клавиши» → внизу 12 px
«Пробел откладывает текущий кадр в выбранную папку».

Никакого мастера, тура и запроса «оценить приложение».

**Пустая папка.** «В папке нет изображений» + имя папки + «Поддерживаются JPEG, PNG,
WEBP, HEIC, AVIF, GIF, BMP, TIFF» + кнопки «Открыть другую» / «Показать в Проводнике».

**Drag-over.** Инсет-рамка 2 px dashed `accent` с отступом 24 px + заливка `accent @ 8%`,
100 мс.

**Целевая папка не задана** — точечная настройка, а не мастер. Папка не спрашивается на
старте. В капсуле чип `Куда сохранять? →` без пульсации. При первом `Space` без цели
открывается пикер, и **после выбора действие выполняется**: нажатие не теряется.

**Загрузка кадра.** Blur-up: шелл-миниатюра, blur 12 px, поверх — полное изображение
через 60 мс opacity. Кольцо-индикатор 24 px появляется только через **400 мс** отсутствия
любого содержимого, с fade-in 80 мс — защита от вспышки индикатора.

**Битый / неподдерживаемый файл.** Карточка 320 px по центру кадра, radius 12,
`surface-elevated`, тень: иконка 24 `warning` → Body Strong «Не удалось открыть
DSC_0491.NEF» → Body `text-secondary` с причиной → кнопки. **Навигация стрелками работает
поверх карточки — застрять невозможно.** Кнопка «Скопировать всё равно» доступна всегда:
неспособность отрисовать превью не должна блокировать основное действие приложения.

**Ошибки** — таблица в §5.8 и §8.5. Все неблокирующие, все с одним действием, все
дублируются состоянием чипа.

### 7.9 Доступность

Здесь не экономим — на XAML-рендере это стоит почти ноль, и именно поэтому мы
отказались от SwapChainPanel.

- **Клавиатура — 100%.** Каждое действие имеет клавишу. `Tab` вызывает хром и держит его,
  пока фокус внутри. `Esc` возвращает фокус на канвас.
- **Фокус.** Родное двойное кольцо WinUI (`FocusVisualPrimary`/`Secondary`), не
  перерисовываем. Работает и над акрилом, и над любой фотографией. Канвас тоже фокусируем
  и получает инсет-кольцо. **Фокус никогда не убирается стилями** — соблазн реальный
  в минималистичном тёмном UI.
- **Контраст.** `text-primary` ≈15:1, `text-secondary` ≈7.2:1, все >4.5:1. Значимые
  обводки и глифы ≥3:1. Гарантия поверх произвольных фото обеспечена инвариантом §7.5.
- **Цвет никогда не единственный носитель смысла.** «Сохранено» = цвет + **цифра** +
  форма бейджа. Ошибка = красный + треугольник + текст.
- **Скринридер.** `AutomationProperties.Name` на канвасе = «DSC_0491.jpg, изображение
  128 из 940, сохранено в Печать». Смена кадра — `RaiseNotificationEvent`,
  `NotificationProcessing.MostRecent`, **с троттлингом 350 мс**: иначе быстрое листание
  превращается в неразборчивый поток речи. Результат копирования — `MostRecent`.
  Ошибки — `ImportantAll`. Тост — live-region.
  **При активном скринридере автоматически включается «Всегда показывать панель»** —
  интерфейс, существующий только при наведении мыши, для незрячего пользователя не
  существует вовсе.
- **Высококонтрастная тема.** Все цвета через `ThemeResource`, ни одного захардкоженного.
  В HC акрил и Mica отключаются полностью, панели получают обводку 1 px `WindowText`
  (в HC поверхности различимы только границами), цвета слотов → системные кисти + цифра.
  Фон канваса становится системным `Window`: читаемость важнее нейтральности фото.
- **Масштаб текста** (100–225%) — отдельная от DPI настройка. Высоты элементов заданы
  как `MinHeight`, не `Height`; ни одного фиксированного по ширине текстового контейнера;
  проверка макета на 200% обязательна. Размер бейджей к масштабу текста не привязан.

Все системные настройки — с подпиской на изменение в рантайме, без перезапуска.

## 8. Форматы и краевые случаи

### 8.1 Что реально есть в системе

**Замерено на этой машине.** Установленные Store-расширения:
`HEIFImageExtension 1.2.48`, `HEVCVideoExtension 2.5.33`, `WebpImageExtension 1.2.31`,
`AV1VideoExtension 2.0.30`, `RawImageExtension 2.5.24`.

RAW-расширение покрывает: `.3FR .ARI .ARW .BAY .CAP .CR2 .CR3 .CRW .DCS .DCR .DRF .EIP
.ERF .FFF .IIQ .K25 .KDC .MEF .MOS .MRW .NEF .NRW .ORF .ORI .PEF .PTX .PXN .RAF .RAW
.RW2 .RWL .SR2 .SRF .SRW .X3F .DNG`.

`Microsoft JPEG XL Decoder` → `.JXL` зарегистрирован. Это **не inbox-кодек**, а
Store-расширение JPEG XL Image Extension, доступное с 24H2 — на чистой машине его
может не быть.

### 8.2 Таблица форматов

| Формат | WIC inbox | Нужен пакет | Вердикт |
|---|---|---|---|
| JPEG, PNG, BMP | ✅ | — | **v1** |
| GIF | ✅ (кадры отдельно, без композитинга) | — | **v1**, первый кадр |
| TIFF | ✅ (LZW/Deflate/JPEG-in-TIFF; JBIG нет) | — | **v1**, страница 1 + бейдж «1/N» |
| ICO | ✅ (все размеры как frames) | — | **v1**, брать самый крупный кадр |
| JPEG XR, DDS | ✅ | — | **v1** бесплатно, никто не заметит |
| WebP | ❌ | `WebpImageExtension` (обычно предустановлен) | **v1** |
| **HEIC/HEIF** | ❌ | `HEIFImageExtension` **+ HEVC-декодер** | **v1**; **самый частый отказ у пользователей** |
| AVIF | ❌ | `AV1VideoExtension` (бесплатный) | **v1** |
| JPEG XL | ❌ | JPEG XL Image Extension (24H2+) | **v1 «по факту»** — просто пробуем декод |
| RAW | ❌ | `RawImageExtension` (бесплатный) | **v1** |
| SVG | ❌ | — | **v2** (`SvgImageSource`). Не формат для сортировки фото |
| PSD, EXR, HDR, JP2 | ❌ | — | **никогда** |

**Про HEIC — уточнение, которое ломает людям день.** `HEIFImageExtension` разбирает
контейнер, но пиксели внутри закодированы HEVC. Без HEVC-декодера файл не откроется,
и ошибка будет выглядеть как «повреждённый файл», а не «нет кодека». Бесплатный листинг
«HEVC Video Extensions from Device Manufacturer» существует и функционально идентичен
платному, но Microsoft показывает его не на всех устройствах.

### 8.3 Как определять поддержку — и почему не так, как хочется

Соблазн: перечислить установленные WIC-кодеки при старте и построить фильтр расширений.

**Замерено: не работает.** В классической категории реестра
`HKLM\SOFTWARE\Classes\CLSID\{7ED96837-96F0-4812-B211-F13C24117ED3}\instance` лежит
ровно **2 записи** — RAW и JPEG XL. Ни встроенных JPEG/PNG/TIFF, ни MSIX-упакованных
HEIF/WebP/AV1 там нет: пакетные COM-регистрации живут в каталоге MSIX, а не в HKCR.
Перечисление даст ложноотрицательные ответы по половине форматов.

> Эта ловушка сработала прямо при подготовке документа: один из проверяющих агентов
> перечислил реестр и заключил, что HEIF-расширения в системе нет. `Get-AppxPackage`
> показывает `Microsoft.HEIFImageExtension 1.2.48.0` — оно установлено. **Единственный
> надёжный способ узнать, откроется ли конкретный файл, — попробовать его открыть.**
>
> **Но список поддерживаемых расширений получить всё-таки можно** — не из реестра,
> а у самого WIC: `BitmapDecoder.GetDecoderInformationEnumerator()` видит и
> MSIX-упакованные кодеки. Замерено на вехе 6: в выдаче есть `.heic`, `.avif`,
> `.webp`, `.jxl` и весь RAW. Это не заменяет попытку декода (кодек может быть
> установлен, но конкретный файл битый), зато даёт точный ответ на вопрос
> «а вообще-то этот формат тут поддерживается» — и пишется в лог при старте.

**Правильный минимум:**

1. **Перечисление папки** — по статическому списку расширений (нужна скорость, не точность).
2. **Реальный ответ** — попытка декода. WIC вернёт конкретный HRESULT.
3. **Ссылка в Store** — не зашивать ProductId (меняются), использовать поиск:
   `ms-windows-store://search/?query=HEIF Image Extensions`. Если Store выключен
   (LTSC, корпоративная политика) — показать название пакета текстом.
   Две строки: `Process.Start` с `UseShellExecute=true` в `try/catch`.

**Коды HRESULT** (проверены по [COM Error Codes (Codec)](https://learn.microsoft.com/en-us/windows/win32/com/com-error-codes-10) —
ходовые таблицы в интернете содержат ошибки, из-за которых «нет кодека» и «битый файл»
показываются наоборот):

| HRESULT | Константа | Что показать |
|---|---|---|
| `0x88982F50` | `WINCODEC_ERR_COMPONENTNOTFOUND` | **Неоднозначен**, см. ниже |
| `0x88982F07` | `WINCODEC_ERR_UNKNOWNIMAGEFORMAT` | «Не изображение / повреждён» |
| `0x88982F60` | `WINCODEC_ERR_BADIMAGE` | «Файл повреждён» (частично может отрисоваться) |
| `0x88982F61` | `WINCODEC_ERR_BADHEADER` | «Файл повреждён» |
| `0x88982F0C` | `WINCODEC_ERR_NOTINITIALIZED` | «Файл пустой или недокачан» |
| `0x88982F8C` | `WINCODEC_ERR_INSUFFICIENTBUFFER` | Обычно «слишком большой» |
| `0x88982F04` | `WINCODEC_ERR_WRONGSTATE` | Внутренняя ошибка, в лог |
| `0x88982F0B` | `WINCODEC_ERR_UNSUPPORTEDVERSION` | «Версия формата не поддерживается» |

> **`COMPONENTNOTFOUND` нельзя переводить как «нужен кодек».** Поймано на вехе 1:
> файл в **0 байт** отдаёт именно этот HRESULT, и приложение советовало поставить
> расширение из Store для пустого `.jpg`. WIC возвращает его и когда кодека нет,
> и когда поток невозможно опознать.
>
> Разбор в v1:
> 1. `Size == 0` проверяем **до** декода — это обычно «файл скачивается прямо сейчас».
> 2. `COMPONENTNOTFOUND` **и** расширение из списка требующих пакета
>    (`.heic .heif .avif .jxl .webp` + RAW) → «Нужен кодек» + ссылка в Store.
> 3. Иначе → «Формат не распознан или файл повреждён». Совет, который пользователь
>    не может выполнить, хуже отсутствия совета.

### 8.4 EXIF-ориентация

Самая частая ошибка просмотрщиков. WIC **не** применяет ориентацию сам. Проводник и
«Фотографии» — применяют. Итог: ваши портреты лягут набок, а у Проводника — нет,
и виноваты будете вы.

**Все восемь значений 1–8**, включая зеркальные 2/4/5/7. Половинчатая поддержка
(только 1/3/6/8) — типичный баг.

**Двойной поворот на HEIC** — классика: файл с айфона имеет и контейнерный `irot`,
и EXIF-тег; декодер применил первый, вы применяете второй, картинка лежит набок
в другую сторону. **Для `.heic/.heif/.avif` EXIF-ориентацию игнорировать.**

Если веха 1 (§6.3) выберет `GetSoftwareBitmapAsync` — `ExifOrientationMode.RespectExifOrientation`
закрывает всё это одним параметром, включая HEIC. Если выберет `DecodePixelWidth` — тег
читается из `BitmapDecoder.BitmapProperties` и применяется `RotateTransform` на `Image`.

**Порядок применения важен:** декод → **ориентация** → расчёт «вписать», исходных W/H,
шага зума. Если посчитать fit до поворота, портрет получит поля не с тех сторон и
«100%» будет врать.

**Ориентация — только для показа.** Копирование — `File.Copy` байт-в-байт (§5.3).

### 8.5 Управление цветом

**Честный v1: всё в sRGB и на этом останавливаемся.**

| Слой | v1 |
|---|---|
| Встроенный ICC | Конвертировать в sRGB |
| Нет профиля | Считать sRGB (верно в 99% случаев) |
| Display P3 / Adobe RGB | Конвертируются в sRGB → на wide-gamut выглядят чуть блёкло, но **не** пересыщенно. Это то, что делает большинство приложений |
| Профиль **монитора** | Игнорировать |
| HDR-мониторы | Ничего не делать. Мы SDR-поверхность, Windows масштабирует по слайдеру «Яркость SDR-контента» |
| HDR-**контент** (AVIF PQ/HLG, Ultra HDR) | Декодируем базовый вариант. **Будет выглядеть тускло — это ожидаемо, не баг.** Бейдж «HDR → SDR» |

**Управление цветом входит в v1 — вопрос закрыт замером.** ICC-конвертация через
`ColorManagementMode.ColorManageToSRgb` стоит **1,1 мс** на кадр (§6.3.1), то есть
меньше процента бюджета декодирования. Фотографии в Adobe RGB (типовой вывод зеркалок)
не поедут в пересыщенные. Никакого «известного дефекта» здесь нет.

### 8.6 Патологические файлы

| Случай | Поведение |
|---|---|
| **100+ МП** | 20000×10000 BGRA = 800 МБ. Читать только заголовок → декодировать с целевым размером ≈2× ширины монитора |
| **Decompression bomb** | PNG 30000×30000 из нулей ≈ 2 КБ на диске → 3,6 ГБ в памяти. Мягкий порог 100 МП (инлайн-кнопка «открыть?», не модалка), жёсткий 512 МП → отказ |
| **Целочисленное переполнение** | `w*h*4` для 536 МП переполняет `int32` — проверка проходит, аллокация падает. Считать в `long`, `checked` |
| **PNG вообще** | Scaled decode **невозможен** (inflate + defilter всего кадра). 24 МП PNG = 300–600 мс, худший случай в приложении. Митигация: держать в кэше дольше остальных; скриншоты (частый PNG) обычно ≤4 МП |
| **Прогрессивный JPEG** | Замерено: 231 мс на 8,3 МП, не масштабируется при декоде. Скрытый ×2–3 на веб-корпусе. Ничего не делаем, но знаем |
| **Битые / обрезанные** | Показать то, что декодировалось, + бейдж «повреждён». Копирование **разрешить**: битым может быть только хвост |
| **`.jpg`, который на самом деле PNG** | WIC определяет по магическим байтам — откроется. Расширение только для перечисления |
| **Нулевой размер** | Обычно файл скачивается прямо сейчас. Карточка «пустой файл», **не удалять из списка**, повторить при следующем заходе |
| **Заблокирован другим процессом** | Открывать `FileShare.ReadWrite \| FileShare.Delete` — `Delete` позволяет удалить файл, пока мы его читаем |
| **Мы сами держим файл** | Классический баг просмотрщиков: пользователь не может удалить файл. Всегда: свой `FileStream` → декод → `Dispose` потока. Проверяется в DoD |
| **1×1** | Клампы в математике зума. «Вписать» = `min(scale, 1)` |
| **Панорама 20000×200** | Лимит текстуры 16384 → §6.7, битмап ≤8192 по стороне |
| **DPI-метаданные картинки** | Игнорировать полностью, считать масштаб от пиксельных размеров |
| **`.lnk` / `.url`** | Ярлык — не изображение. Не разрешать |

**Безопасность:** декодеры изображений — исторический RCE-вектор. Реальная защита —
декод в отдельном low-privilege процессе; это **никогда** для v1. Минимум:
не запускать приложение с повышенными правами (`asInvoker` в манифесте) и не отключать
штатные митигации.

### 8.7 Файловая система

**Длинные пути.** В `app.manifest` — `longPathAware=true`. Префикс `\\?\` руками
**не** добавлять: он отключает нормализацию и ломает пути из drag&drop. Ловить
`PathTooLongException`.

**Unicode.** Не резать имена через `Substring` — рвёт суррогатные пары и составные
эмодзи. Обрезку отдать `TextTrimming`. **Bidi-спуфинг:** имя с U+202E выворачивает
заголовок — вырезать `\u200E\u200F\u202A-\u202E\u2066-\u2069` **при показе**, не при
работе с файлом. **Сделано на вехе 5** — одна строка regex плюс пять проверок
в self-test. **NFC/NFD:** файлы с macOS/Samba могут отличаться
нормализацией — сравнивать через `OrdinalIgnoreCase`, отображать как есть, **не**
нормализовывать (получите путь, которого нет на диске).

**Сеть и UNC.** `EnumerateFiles` (ленивая), никогда `GetFiles`.
`EnumerationOptions { IgnoreInaccessible = true }` — иначе одна недоступная запись
убивает всё перечисление посреди итерации. **Не вызывать `File.Exists` /
`GetLastWriteTime` в цикле** — данные уже пришли из `WIN32_FIND_DATA` вместе с `FileInfo`.
**Честно про отмену:** зависший SMB-вызов не отменяется `CancellationToken`, поток
блокируется до таймаута ОС. Стратегия: не блокировать UI, отбрасывать результат по
токену, не плодить новые запросы. Не притворяться, что отмена мгновенна.

**OneDrive / Dropbox — files-on-demand.** Самый коварный пункт: перечисление мгновенно,
а **чтение** заглушки запускает загрузку из облака на минуты — и префетч соседей
превращает приложение в кирпич.

Определение по `FileAttributes` (ноль IO, данные уже есть):
`Offline 0x1000`, `RecallOnOpen 0x40000`, **`RecallOnDataAccess 0x400000`** — основной
флаг заглушки.

1. Заглушки **никогда** не префетчить — пропускать молча.
2. Открыл явно → карточка «файл в облаке» + скачать по `Enter`, с прогрессом и отменой.
3. Ловить `ERROR_CLOUD_FILE_*` — отдельная категория ошибки, не «файл повреждён».
4. Копирование заглушки — это тоже полная загрузка. Показать в тосте «скачивание…»,
   а не молча подвесить.

**Прочее.**

| Случай | Поведение |
|---|---|
| Флешку выдернули | Не 500 карточек ошибок — одно состояние экрана «диск отключён» + кнопка. Определять по недоступности корня |
| Файл удалили/переименовали снаружи | Мы его не держим. Тост «файл больше не существует», элемент убрать, перейти к следующему — по правилу §6.1 |
| Целевая папка внутри исходной | Перечисление РЕКУРСИВНОЕ, поэтому целевые папки исключаются из обхода по списку слотов — иначе список рос бы с каждым копированием |
| Та же картинка уже сохранена | Сверка по содержимому, рекурсивно по дереву слота (§5.8). Копия не создаётся, показывается заметное уведомление с путём |

### 8.8 FileSystemWatcher — не в v1

Известные и неустранимые проблемы: буфер 8 КБ по умолчанию (максимум 64), переполнение →
потерянные события; 2–4 события `Changed` на одно изменение; на сетевых путях зависит
от сервера, на части NAS не работает вовсе; облачные папки генерируют шторм от клиента
синхронизации; извлечение носителя убивает watcher тихо; переименование самой папки
не отслеживается.

**Замена, ~10 строк и ноль классов отказа:** обработчик `Activated` — если
`Directory.GetLastWriteTimeUtc` изменилась, пересканировать (сохранив позицию **по пути**,
не по индексу). Плюс `F5`. Юзкейс — сортировка уже существующей папки; живой мониторинг
там не нужен.

### 8.9 Дисплей

| Случай | Поведение |
|---|---|
| Разный DPI на мониторах | `PerMonitorV2` в манифесте. `DpiChanged` → перезапрос кадра в новом квантованном тире (§6.4) |
| Перенос окна между мониторами | То же событие. Fullscreen — по монитору текущего окна, не по основному |
| Смена разрешения / поворот экрана | Вернуть окно в границы экрана, пересчитать fit |
| Смена системной темы на лету | `Application.RequestedTheme` + `UISettings.ColorValuesChanged` |
| Высокая контрастность | §7.9 |
| RDP / удалённый сеанс | Выключить Mica и акрил, иначе прокрутка станет слайд-шоу |
| Device lost | На XAML-рендере ничего делать не нужно, композитор восстановится. Появится свой SwapChainPanel — появится и обязанность |

### 8.10 Ошибки, логи, восстановление

**Не уронить приложение.** Декод — всегда в фоне, всегда в `try/catch` вокруг **всего**
декода, ловя широко: `COMException`, `FileFormatException`, `NotSupportedException`,
`IOException`, `UnauthorizedAccessException`, `ArgumentException`, `OutOfMemoryException`.

> `ponytail:` `OutOfMemoryException` в .NET формально невосстановима, но здесь она
> приходит из конкретной крупной аллокации декодера — поймать, освободить кэш, показать
> «файл слишком большой» и жить дальше практично.

Глобальные сети безопасности: `Application.UnhandledException`,
`AppDomain.CurrentDomain.UnhandledException`, `TaskScheduler.UnobservedTaskException` →
дописать в `%LocalAppData%\Gallery\crash.log` (последние 10 записей) и показать полоску
«что-то сломалось, открыть лог». Не глотать.

**Логи.** `%LocalAppData%\Gallery\logs\app-YYYYMMDD.log` — **Local**, не Roaming.
Ротация: файл на день, при старте удалить всё старше 7 дней. Три строки, без библиотеки.
Пишем warn/error + **одна строка при старте**: версия приложения, сборка ОС, DPI
мониторов, список установленных image-расширений. Именно эта строка отвечает на 90%
будущих «почему не открывается HEIC». Не логировать на горячем пути.

**Крэш-репорты.** Телеметрии нет. Windows Error Reporting уже собирает падения локально.
Отправка куда-либо — **никогда** без явного согласия.

**Настройки — тихий убийца старта.** Запись **атомарная**: сериализовать в `.tmp` →
`File.Move(overwrite: true)`. Иначе падение в момент записи оставит обрезанный JSON, и
приложение **больше не запустится** — самый обидный класс отказа. Чтение: битый JSON →
переименовать в `settings.bad`, стартовать с дефолтами, залогировать. **Никогда**
не падать из-за настроек.

### 9.3 План работ

Каждый этап заканчивается запускаемым exe, который делает что-то видимое. Ни один
этап не «подготовительный».

**Веха 0 — ВЫПОЛНЕНА. Замер, от которого зависел стек.**
Результаты — §2.4. Гейт 1200 мс не сработал (885 мс), WinUI 3 подтверждён.

Попутно выяснено:
- **Пакета шаблонов `Microsoft.WindowsAppSDK.ProjectTemplates` не существует**
  (`dotnet new install` → «Пакет не существует», exit 103). Шаблоны WinUI не нужны:
  csproj и четыре файла пишутся руками и собираются с первой попытки. Проверенная
  конфигурация — §9.4.
- `EnableMsixTooling=true` в unpackaged-сборке работает и ничего не ломает.
- **`PublishSingleFile` для WinUI 3 работает** — закрыт открытый вопрос §10.4.3.
  Один exe 227,3 МБ запускается; распаковка 451 файла в `%TEMP%` происходит один раз
  на версию (+235 мс к первому запуску, дальше из кэша).
- `PublishReadyToRun` обязателен, см. §2.4.

*Поставка:* single-file для раздачи (один файл вместо 451 — снимает целый класс
«а почему на другой машине не запустилось»), папка для разработки (публикация быстрее).

**Веха 1 — ВЫПОЛНЕНА. Окно, которое показывает картинку.**

Snap Layouts целы), argv → открыть файл или папку, `FolderList` с натуральной
сортировкой через `StrCmpLogicalW`, `Decoder` по пути A, стрелки / `PgUp` / `PgDn` /

`--bench-decode`, генератор корпуса `tools/gen-testdata.py` (20 файлов).

Проверено на живом приложении, а не в теории:
- EXIF-ориентация применяется (портрет 1200×1800 с тегом 6 показан как 1800×1200,
  метка «TOP» ушла вправо — верно для ориентации 6);
- натуральная сортировка ставит `img_2` перед `img_10`;
- `--self-test` — 16 проверок, все проходят;
- битый и пустой файлы дают карточку, приложение не падает, навигация поверх неё живёт;
- размеры в статусе показываются **после** поворота — то, что человек видит.

Замеры: 165 МБ на одном 24 МП кадре, 179 МБ после 13 кадров подряд (стабильно).
**Известный дефект вехи 1:** при листании быстрее ~120 мс память растёт до 251 МБ —
декоды запускаются и отменяются, но успевают отработать. Это ровно то, что чинит
дебаунс 120 мс на вехе 3; отдельного фикса здесь не делаем.

> **Поймано и исправлено:** переиспользование одного `SoftwareBitmapSource` вместо

**Сделано:**

**Пять исправлений корректности, найденных аудитом:**

1. `GetAsync` отдавал второму заказчику задачу, привязанную к токену первого:
   отмена навигации выбрасывала уже декодированный кадр. Теперь токен гасит

2. `OnResizeSettled` безусловно обнулял `Img.Source`, а восстанавливал только

   можно было скопировать не то, что на экране.
4. `OnClosing` был реентерабелен — второй Alt+F4 поверх диалога вызвал бы второй

5. Ошибочный тост гас сам через 6 с, хотя §7.3 требует обратного; красного
   состояния у чипа слота не было вовсе.

**Замерено после всех правок:** тёплый старт **263 мс** (медиана 6 прогонов),
self-test — **82 проверки** (45 из них проверяют, что каждый токен палитры есть
во всех трёх словарях: опечатка в одном всплыла бы только у пользователя с
высокой контрастностью). Сборка одним файлом — 228,2 МБ, запускается.

> **Правка к §8.3.** Спецификация утверждала, что перечислить установленные кодеки

> по-прежнему не замена попытке декода, но для диагностики — точный ответ,

**Аудит закрыт полностью: 15 блокеров, 39 важных, 16 мелочей.**
Семнадцатая мелочь — «диспозить `CancellationTokenSource` при замене» — оставлена
намеренно: токены отменённых источников живут внутри уже запущенных декодов
(`Decoder.ReadAsync(ct)`, `_gate.WaitAsync(ct)`), и `Dispose` дал бы шанс словить
`ObjectDisposedException` вместо штатного `OperationCanceledException` на пути,
который сейчас работает. Экономия нулевая, риск ненулевой.

Что дал второй проход:

- **Клавиатура доведена до §4.1:** `Enter` как синоним пробела, `+` `=` `−`
  основного ряда (числовой `Key` в XAML не записывается, акселераторы задаются
  кодом; `+` на большинстве раскладок — это `Shift+=`, поэтому их два), `Ctrl+W`.
- **Панели забирают клавиатуру целиком.** Пока открыты настройки или шпаргалка,
  цифры и пробел принадлежат им — иначе нажатие в панели копировало файл.
- **Единственный экземпляр.** `AppInstance.FindOrRegisterForKey` +
  `RedirectActivationToAsync`. Служебные флаги (`--bench`, `--startup-probe`)
  редирект пропускают мимо, иначе они уехали бы в чужой процесс и молча завершились.
- **Перечисление папки ушло с UI-потока.** Открытие файла показывает кадр
  немедленно, полный список догоняет асинхронно, позиция восстанавливается по пути.
- **Недоступная папка отличается от пустой.** «Нет доступа» больше не выглядит
  как «здесь нет картинок».
- **Отметки и отказы слотов видимы:** красный чип при исчезнувшей папке, отдельный
  текст «слот недоступен», строка про отключённые отметки при 50 000 файлов.
- **Масштаб текста** из специальных возможностей применяется к дереву; хром не
  прячется при активном скринридере и при клавиатурном фокусе внутри него.
- **Тема настраивается** — тёмная, светлая, как в системе.

Пять исправлений корректности второго прохода:

1. Повторная постановка того же файла в слот до записи на диск давала тот же
   `target`, и вторая копия падала на `File.Move`. Учитываем запланированное,
   переиспользуя `ResolveTarget`, — `HashSet` тут не годится: он заставил бы
   считать «уже там» и *другой* файл с тем же именем, то есть тихо его не скопировать.
2. `OnSettle` не отличал отмену от настоящего отказа декодирования — второй
   оставлял пустой холст навсегда.
3. `Fail()` не звал `DropFull`/`DropThumb`: `_full` навсегда блокировал
   полноразмерный декод и держал память.
4. Битмап не освобождался на путях раннего выхода в `OnFullTimer` и при броске
   из `SetBitmapAsync`.
5. `crash.log` рос бесконечно.

> **Мина unpackaged-приложения, найденная запуском.** `AppInstance` перенаправляет
> активацию, но **не передаёт аргументы**: у unpackaged-экземпляра
> `ILaunchActivatedEventArgs.Arguments` пуст, а своего канала для полезной нагрузки
> WinAppSDK не даёт. Проверено: без обходного пути редирект работает, окно выходит
> на передний план, а файл не открывается. Путь передаётся через одноразовый файл
> `handoff.txt` рядом с настройками.

**Третьим проходом закрыты мелочи.** Из заметного: геометрия окна сохраняется
через `WINDOWPLACEMENT` (он сам валидирует координаты против текущей конфигурации
мониторов и переживает «развёрнуто»); слот можно отвязать; Mica стала видна на
полосе заголовка — фон уехал с `Root` на холст, иначе непрозрачная заливка
перекрывала бэкдроп и строка его назначения была мёртвой; остаток накопителя
колеса обнуляется при смене направления; список расширений для `Ctrl+O` стал общим
с перечислением папки; брошенный файл неподдерживаемого формата и несуществующий
путь в аргументах наконец дают обратную связь.

> **Главная находка третьего прохода — не мелочь.** Геометрия упорно не
> сохранялась, и причина оказалась глубже: **`Window.Close()` не поднимает
> `AppWindow.Closing`**. То есть защита §5.5 — дождаться очереди копий перед
> закрытием — работала только при клике по крестику, а `Ctrl+W` и последний `Esc`
> закрывали окно молча, теряя незаписанные копии. Логика вынесена в
> `PrepareCloseAsync()`, и оба пути идут через неё. Нашлось только замером:
> в коде это выглядело правильно.

**Четвёртый проход — по замечаниям с живого использования.** Шесть правок,
из которых две вскрыли настоящие ошибки, а не вкусовщину:

1. **Подсказка хоткея посреди картинки.** WinUI сам показывал ярлык акселератора
   при наведении: на полноэкранном холсте это прямоугольник со словом «Вправо».
   `KeyboardAcceleratorPlacementMode="Hidden"` на корне.
2. **Переход к кадру по номеру** — клик по счётчику `N / M` (§4.6).
3. **Позиция помнится по папкам** (§4.6).
4. **Листание колесом не работало никогда.** `ScrollView` съедал колесо в
   `InteractionTracker`; лечится `IgnoredInputKinds`, см. §4.7.
5. **Панорамирование не работало никогда.** `ExtentWidth` — размер до зума, см. §4.7.
6. **Двойной клик всегда возвращает «вписать»**, а не переключает на 100%.

> Пункты 4 и 5 — цена ставки на `ScrollView` из §4.7, и оба прошли три
> предыдущих прохода незамеченными: код читался правильно, а обработчики просто
> не вызывались. Ловится только тем, что руками дёргаешь мышь у запущенного
> приложения. Отдельная ловушка автоматизации: `SetCursorPos` перемещает курсор,
> но не порождает событий указателя для WinUI, — первые прогоны показывали
> «пан не работает» уже после того, как он заработал. Инжектировать надо
> `mouse_event(MOUSEEVENTF_MOVE)`.

**Замерено после всех проходов:** self-test — **133 проверки** (45 из них
сверяют, что наборы ключей во всех трёх словарях тем совпадают и каждое значение —
кисть), прогон из 14 команд подряд без падений, копирование и отмена работают,
геометрия окна восстанавливается точно, `crash.log` пуст.

**Пятый проход — лента миниатюр (§4.8).** Из четырнадцати находок разбора приняты
одиннадцать. Три отклонены осознанно: бейджи слотов в ленте (рябь на ячейке 80×60),

> `Decoder.ThumbnailAsync` было очевидным решением: он уже написан, стоит 1–2 мс и
> уже применяется как заглушка. Он **не применяет EXIF-поворот** — и на холсте это
> не видно, потому что заглушка живёт 120 мс. В ленте она постоянна, и все
> вертикальные кадры легли бы набок навсегда. Замена на миниатюру оболочки заодно
> убрала запасной путь через полный декод, чтение 512 КБ в LOH на каждый файл и
> весь вопрос владения `SoftwareBitmap`.

> **Вторая находка того же сорта.** Анимация сдвига перезапускалась с `From=dx` на
> каждом шаге, то есть при автоповторе 30 Гц — каждые 33 мс при длительности 120 мс.
> Лента не ехала бы, а дрожала на месте. Правило §7.6 «глушить анимацию, когда
> события идут чаще неё» было записано за четыре прохода до этого и всё равно
> нарушено: записать правило и применить его — разные действия.

**Замерено после пятого прохода:** self-test — **157 проверок** (24 новые держат
единственный инвариант ленты: середина ряда — текущий кадр); смена кадра из кэша
p50 0,37 мс / p99 3,01 мс с лентой против p50 0,22 / p99 0,67 без неё; лента
показана, скрыта и возвращена клавишами `T` и `F4`; клик по третьей ячейке справа
от центра после `Home` открыл четвёртый файл папки, и следующий `Space` его
скопировал — то есть фокус вернулся на холст.

**Шестой проход — сохранение сессии.** Жалоба была простая: «закрыл приложение,
а там старая папка и картинка». Штатный круг — открыть без аргументов, полистать,
закрыть, открыть снова — при этом работал безупречно, и три круга подряд вернули
ровно то, на чём кончили. Ошибки нашлись в путях, которые этот круг не задевает.

1. **`FolderLast` не писался на закрытии** (см. §4.6). Видно только при закрытии
   в первые 120 мс после шага и только при следующем явном открытии той же папки.
2. **Запись сессии зависела от захвата геометрии окна.** В `PrepareCloseAsync`
   `WindowPlacement.Capture()` стоял ПЕРЕД `Flush()` в общем `try`. Любое его
   исключение уводило в `catch`, который возвращал `true` — приложение спокойно
   закрывалось, не записав ни кадра, ни папки. Теперь сессия пишется первой и
   своим `Flush`, геометрия — вторым блоком со своим `catch`. Спровоцировать
   исключение я не смог, так что это исправление по рассуждению, а не по замеру;
   но порядок, при котором приятная мелочь способна унести главное, неправилен
   независимо от того, стреляет он сегодня или нет.
3. **Свежесть папок опиралась на порядок словаря** (см. §4.6).

> **Чему стоит поучиться на третьем пункте.** Он был написан в пятом проходе,
> выглядел очевидно верным и прошёл сборку. Свалила его самопроверка, добавленная
> в том же проходе, — на втором же утверждении: «повтор поднимает наверх» вернул
> прежний порядок. Ни чтение кода, ни ручной прогон этого бы не показали: разница
> проявляется только на папке, открытой повторно, и только через несколько
> сессий. Проверка на чистой функции стоила десяти строк и поймала ошибку,
> которая иначе жила бы месяцами.

**Седьмым проходом запись сессии стала немедленной** (§4.6): дебаунс в секунду
снят с позиции и оставлен остальным настройкам. Это закрывает последнюю дыру из
шестого прохода — потерю состояния при нештатном завершении.

**Замерено после шестого прохода:** self-test — **181 проверка**; шаг и немедленное
закрытие сохраняют кадр и в `LastPath`, и в `FolderLast`; `Ctrl+W` и крестик оба
выходят и пишут одно и то же; явное открытие папки возвращает на сохранённый кадр;
геометрия окна по-прежнему сохраняется.

**Восьмым проходом добавлен перевод через API** (§4.10). Локальный путь к тому
моменту упёрся в потолок, и это было измерено, а не предположено:

- **`opus-mt-tc-big-en-ru` не существует.** Семейство tc-big покрывает турецкий,
  испанский, португальский, корейский, арабский — русского в нём нет. Замена
  чекпойнта без единой правки в коде отпадала.
- **Лучевой поиск ничего не дал.** Ширина 4 против жадного: 4 различия из 7,
  но выигрыша нет — где-то лучше («если я **это** сделаю»), где-то хуже
  («Я сказал» вместо «Я же говорил»), однажды потерялась точка в конце. Стоит
  в 1,8 раза дороже. Идиома не понята обоими: это предел модели, а не декодирования.
- **GTX 1050 с 2 ГБ** не вмещает даже 3B в int4 — локальная мультимодальная
  модель закрыта железом.

> **Что здесь стоит запомнить.** Три из четырёх наблюдаемых дефектов перевода
> оказались не дефектами переводчика. «Простите, что опоздала» — это не ошибка
> Marian, а отсутствие входных данных: пола говорящего нет в английском
> оригинале, и взять его неоткуда, кроме как помнить с прошлых страниц. Менять
> модель ради этого бессмысленно; менять надо то, ЧТО ей отправляют.

**Замерено после восьмого прохода:** self-test — **210 проверок** (29 новых
держат порядок чтения и разбор ответа API); откат при недоступном API проверен
на заведомо мёртвом адресе — тост называет причину, страница переводится
локально. Живой вызов API не проверялся: для него нужен ключ пользователя.

### 9.5 Тесты

**Механика: `gallery.exe --self-test`.** `App.OnLaunched` смотрит argv, вызывает
`Checks.Run()`, печатает результат, выходит с кодом 0/1. Никакого второго проекта,
никаких фикстур — проверки гоняются по тому же коду, что и в продакшене.
Для вывода в консоль из WinExe — один `AttachConsole(-1)`.

> `ponytail:` self-test вместо тестового проекта. Апгрейд до xunit — когда проверок
> станет больше ~30 или понадобится CI-репорт.

Автоматически проверяется только то, где ошибка стоит дорого:

| Что | Почему именно это |
|---|---|
| Правило выбора масштаба декода | Ошибка = апскейл (видимое мыло) или лишние 70 МБ и 100 мс. 6000→2560 даёт 3000; 6000→3000 даёт 3000, а не 1500; портретные; крошечные; target = 0 не делит на ноль |
| `Slots.ResolveTarget` | **Единственное место, где можно потерять данные.** Нет файла; есть с тем же размером → NO-OP; есть с другим → `(2)`; есть `(2)` и `(3)` → `(4)`; имя без расширения; имя с точками |
| Вытеснение из кэша | Вытесняется максимально далёкий по индексу, а не давний по времени; окно ±3 не вытесняется никогда; после разворота назад ничего нужного не выброшено; `Dispose` ровно один раз на кадр |
| Натуральная сортировка | `img_2 < img_10`, регистр, кириллица, реверс |
| Мутация списка | После выреза элемента позиция восстановлена **по пути** (§6.1); удаление последнего не выходит за границу |
| Undo-стек | Отмена при подменённом файле пропускает и сообщает, а не удаляет чужое; NO-OP в стек не попадают |
